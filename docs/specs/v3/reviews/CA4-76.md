# CA4-76 — binding enablement through authority transitions

**Status:** specification reviewed (2026-10-13).
**Evidence type:** `textual_contract_and_scenario_review`.
**Runtime test:** `not_run_v3_not_implemented`.

## Decision

A binding is enabled exactly while its Reaction is `automatic`. Layer 5 pushes a typed
`BindingEnablementChange` after an authority transition entering or leaving `automatic` commits;
Layer 6 applies it as a revision of the current publication index with the reconciliation of
Layer 3 §6.3.1.

## Alternatives rejected

- Tracker reads `enabled` from Layer 5 at delivery: a live policy query, forbidden by Layer 3.
- Route authority transitions through the composed configuration generation: contradicts Layer 0
  §4.7 and would make every promotion a configuration commit.

## Performance

Tracker slow path only; no Layer 0/1 involvement; the transition and every cycle never wait;
copy-on-write of the affected keys through a reverse index built at staging; one reference swap;
nothing persisted (rebuilt at start from the generation and the authority projection).

## Scenario review

| Scenario | Result |
|---|---|
| Reaction promoted while its suppression episode is active | Active abstention delivered once. |
| Reaction disabled after a notice was delivered | Notified binding closed with `binding_deactivated`; no restoration later. |
| Same change pushed twice | Second ignored by `authority_transition_id`. |
| Change for a superseded generation | Ignored. |
| Restart | Index rebuilt from active generation and current authority; tracker empty. |

Textual review only; no V3 runtime test has run.
