# CA4-72 — no stored resident text in operational event facts

**Status:** specification reviewed (2026-10-12).
**Evidence type:** `textual_contract_and_scenario_review`.
**Runtime test:** `not_run_v3_not_implemented`.

## Decision (approved with C6)

`OperationalEventValue` drops `title` and `message` and gains `context_version`. Its `context` holds only closed fields and
stable identifiers. Layer 6 renders text at each delivery (recipient locale, core templates,
current configured names); Layer 8 renders history the same way.

## What was actually needed

| Place | Change |
|---|---|
| Layer 1 §3.1 | Value fields, `HeimaEvent` mapping row, adapter validation, no-stored-text rule, follow-up and availability adapter wording, acceptance criteria. |
| Layer 0 §4.5/§4.5.1/§7.4.1/§13 | "Rendered" audit fact wording only; outbox mechanics unchanged. |
| Layer 3 §6.3.1 | The availability adapter derives key and severity, no title/message. |
| Layer 5 §6.0/§8 | Renderer-bound staging obligation removed; "renders as" became "appends as". |
| Overview, recap, support/governance diagram | Renderer-bound obligation and the L6 -> L5 renderer-output edge removed. |
| CA4-01 serialization examples | `title`/`message` removed, `context_version: 1` added; byte counts recomputed (835, 730, 790). |

A stored template reference was considered and not added. Instead `OperationalEventValue` carries
`context_version`, the version of its fact type's context schema: a wording change keeps it, a
field change bumps it, and the core keeps a template per `(fact_type, context_version)` its
retained history can contain. An unknown version renders generic text, never a guessed meaning.
`fact_type` plus the closed context (including phase) select among templates of one version.

## Overlap check

One new field, `context_version`; V3 had no value-schema version for facts, so it duplicates
nothing, and it is limited to the one rendered value type. `notification_key`, `severity`, `context`, `where` and the outbox are
unchanged. The recipient `locale` belongs to the future Layer-6 `NotificationRecipient` (C6).

## Scenario review

| Scenario | Result |
|---|---|
| Advisory delivered to an Italian and an English recipient | One fact; two renderings at delivery. |
| Device renamed after a follow-up warning | History shows the new name; the fact is unchanged. |
| Device removed from configuration | History shows its identifier. |
| Producer puts a display name in `context` | Rejected by the adapter validation. |
| Retry after a crash before `delivered` | Re-rendered from the same fact; same `notification_key`. |
| Core upgrade adds a field to the advisory context | New facts use version 2; old facts still render with the version-1 template. |
| Only the advisory wording changes | Same version; history shows the new wording. |

Textual review only; no V3 runtime test has run.
