# CA4-39 — runtime recovery confirmation lifecycle

**Status:** specification reviewed on 2026-10-05.
**Evidence type:** `textual_contract_and_scenario_review`.
**Runtime test:** `not_run_v3_not_implemented`.

## Impact record

The approved rule invalidates an open recovery confirmation after a process restart and
regenerates it only from fresh observations and current policy. While running, the request
remains valid only while the same proposal is still admissible; a finite time ceiling also
closes it. Layer 0 §7.3 already checkpoints confirmation transitions immediately and §7.4
already produces `require_confirmation` proposals. Layer 0 §5.1 owns trusted response
ingress; Layer 5 owns current target, guard and authority admission.

The gap is a typed request identity, lifecycle, invalidation comparison and response race
rule. The owner is Layer 0 recovery request bookkeeping; Layer 5 supplies and rechecks
the current proposal. Dependent text: Layer 0 §5.1, §7.3–7.4 and acceptance; Layer 5
acceptance; overview, recap and backlog. V3 must retain one generic action path and
clean-start recovery. Counterexamples: a valve request whose new target becomes closed,
an HVAC target whose mode changes, a blind whose observed position already reaches the
proposal, an unreadable actuator, and a response racing a new policy generation.

| ID | Scenario | Required result |
|---|---|---|
| S1 | Valve target and observed state unchanged over repeated cycles | One open id and original 24-hour deadline |
| S2 | Blind position changes, HVAC mode changes, or relevant guard fails | Old id invalidated before a response; any new proposal has a new id |
| S3 | Unrelated fact changes while proposal inputs remain identical | Open request stays valid |
| S4 | Observed channel reaches the target before approval | Close as already satisfied; no command |
| S5 | Channel becomes unreadable or consent is revoked | Invalidate; no approval dispatch |
| S6 | Resident dismisses or the 24-hour ceiling expires | No command and no repeated prompt for unchanged proposal |
| S7 | Two replies or reply racing generation swap | Serialized check admits at most one; stale reply rejected |
| S8 | Crash after checkpointed request creation, then late reply | Old id rejected; fresh complete intake and current calculation may propose new id |
| S9 | Checkpoint commit fails before request creation or approval acknowledgement | No actionable request or dispatch; same-id retry is idempotent |

**Review result:** Layer 0 §5.1, §7.3, §7.4.1 and acceptance, Layer 5 §8, the
overview and recap agree on these outcomes. This is a textual specification review;
no executable V3 runtime test has run.
