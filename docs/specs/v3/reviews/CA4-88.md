# CA4-88 — one detection entity per activity

**Status:** specification reviewed (2026-10-13).
**Evidence type:** `textual_contract_and_scenario_review`.
**Runtime test:** `not_run_v3_not_implemented`.

## Decision (approved, S3 of the CA6 reread)

Layer 8 publishes one `binary_sensor` per activity resolver (scope × `activity_id`). It is `on`
when the claim is `active` and `off` otherwise, including `available=False`: "not detected now",
never "proven inactive". This is the one declared exception to mirroring `available=False` as HA
`unavailable`. No attribute reports an unreadable anchor input. The Layer-1/4 meaning of
`available` is unchanged.

## Alternatives rejected

- One `sensor` enum per room: merges independent claims, which Layer 4 §3.1 forbids, and cannot
  show two coexisting activities.
- `unknown` instead of `off`: an entity that is `unknown` most of the day is unusable in HA
  automations and history.
- One sensor per room with a list attribute: a count is of little use; a "main" activity
  reintroduces a priority Layer 4 forbids.
- No activity entities: loses a useful automation input.

## Overlap check

No new type, field or feed: the entity uses the existing configuration-derived committed-state
subscription (Layer 0 §4.8, Layer 8 §10.3) on the existing `activity.<activity_id>` claim. The
occupancy row and pending-items source were corrected in the same table (CA6 M18).

## Scenario review

| Scenario | Result |
|---|---|
| Kitchen hob on | `cooking` entity `on`. |
| Hob off or its sensor unreadable | `off`, never `unavailable`; the sensor's own unavailability shows in health and diagnostics. |
| Study with `relax` and `working` both active | Two entities, both `on`. |
| Activity resolver removed by a commit | Its subscription stops and its entity is removed. |
| Occupancy whose physical input is unreadable | Occupancy entity `unavailable`, unchanged rule. |
| Future `bipolar` profile | Must declare its own mapping at review. |

Textual review only; no V3 runtime test has run.
