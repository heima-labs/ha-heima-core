# CA4-48 — canonical scope review

**Status:** specification reviewed on 2026-10-05.
**Evidence type:** `textual_contract_and_scenario_review`.
**Runtime test:** `not_run_v3_not_implemented`.

## Impact and resolution

Layer 1 §5 already defines the one canonical `Location` identity for casa,
room, zone and an explicit set of rooms. Layer 3 §4.1.1 and Layer 4 §4.2
introduced `LocationSet` and `house` without a separate definition. Both
administrative staging paths now accept only a `Location`, with the core kind
deciding which `scope` values are legal. The existing Layer-1 validation and
canonical `LocationKey` handle set ordering and one-room sets. A staged zone
additionally fingerprints its resolved, ordered membership so a change in
membership still creates a new generation.

| ID | Scenario | Required result |
|---|---|---|
| S1 | Same explicit room set in different input orders | One `Location(scope="rooms")` identity and fingerprint |
| S2 | One-room set | Use `scope="room"`; malformed `rooms` Location rejected |
| S3 | Whole-house input | Exactly `Location(scope="casa")`; no separate `house` token |
| S4 | Zone membership changes with stable zone id | New staged definition fingerprint and ordinary invalidation |
| S5 | Wildcard or live room query | Rejected before activation |

**Review result:** Layer 3 and Layer 4 use Layer 1's existing scope vocabulary;
no new location type or runtime lookup is needed.
