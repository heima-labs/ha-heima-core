# CA4-128 — evidence source readiness for pending proposals

**Status:** specification reviewed (2026-10-20).
**Evidence type:** `textual_contract_and_scenario_review`.
**Runtime test:** `not_run_v3_not_implemented`.

## Impact record

- **Existing decisions.** Layer 5 §4.1: readiness is not a disposition, `not_approvable` is not
  terminal, a compatible refresh restores it, `evidence_expired` covers evidence past `valid_until`,
  and unavailable required supporting artifacts already make a proposal not approvable (without a
  code). Layer 5 §4.2: pending proposals bound to an invalid dependency become not approvable in the
  same commit. Layer 3 §4.1.2: an invalidated definition produces no candidate and its artifacts are
  unavailable for every egress; a `serving_semantics` change withdraws candidates of the old serving
  generation. The proposal review notice already closes on `not_approvable` and reopens on
  `approvable_again`.
- **Gap.** Layer 5 drew no consequence for an already pending proposal when its learner was removed
  or invalidated or its candidate withdrawn; the proposal stayed approvable until `valid_until`.
  The evidence did not record its source, so a serving withdrawal was undetectable.
- **Overlap check.** Reuses the `(learning_instance_id, serving_generation_fingerprint)` identity of
  Layer 3's adoption chain, Layer 0 §4.7 staging against the Layer-3 generation, the existing
  supporting-artifact resolution, and Layer 0 §5.1 non-forgeability. Rejected: `FactSource` (a
  fact/action provenance type on a governance record) and `ArtifactRef` alone (misses serving
  withdrawal and artifact-less extension analyzers). Observation: Layer 3 §4.2/§4.3 call the same
  administrative instance `learner_id`; not changed here.
- **Owners.** Layer 5 §4.0, §4.1, §4.2, §8. Dependent: Layer 3 §4.1.2, §6.4, §9. Layers 6 and 8,
  overview and recap need no change (the notice reuses existing phases; codes render generically;
  neither orientation document describes readiness codes).
- **V2-to-V3 constraints.** None. The V3 implementation worktree has no Layer-3 or Layer-5 code.

## Decisions (developer-approved 2026-10-20)

1. A pending proposal whose source no longer stands behind it becomes not approvable; one rule for
   core learners and, from CA4-129, extension analyzers.
2. New non-terminal readiness code `evidence_source_unavailable`, conditions (a) source absent or
   invalidated, (b) serving generation superseded, (c) primary or required supporting artifact
   unavailable.
3. `ProposalEvidenceSource(source_kind="learning_instance", source_id, serving_generation_fingerprint)`.
4. Recorded per evidence revision, not on the root.
5. Assigned by the core runtime from the admitted run context; a conflicting payload source is
   rejected at admission.
6. Canonical position immediately after `evidence_expired`.

## Scenario review

| Scenario | Result |
|---|---|
| Administrator removes the learner with a proposal pending | Same commit records `evidence_source_unavailable`; review notice closes. |
| Breaking upstream invalidates the learner; a successor definition re-emits the same candidate | Refresh appends a revision with the successor's source; `approvable_again`; no duplicate proposal. |
| `serving_semantics` change (`objective_id`) | Old proposal not approvable (b); the new payload has a new fingerprint and opens a new proposal. |
| `semantic_only` upstream change | Artifacts unavailable (c); after rebuild a compatible refresh restores approvability. |
| Required supporting artifact stale | Not approvable with the new code (c). |
| Evidence expired and source removed | Both codes, `evidence_expired` first. |
| Acceptance concurrent with a removal commit | Acceptance revalidation rejects with `validation_failed` and the code, or `stale_precondition` if the base generation changed. |
| Restart | Readiness derived from the active generation; no state lost. |
| Candidate payload names another source | Rejected before a proposal root is persisted. |

Textual review only; no V3 runtime test has run.
