## Findings

### F-L1-01 — `UnanimityStrategy.min_available` cited with a default of 1 that Layer 2 forbids

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer1_substrate_spec.md:554` — "e.g. a Layer 2 `UnanimityStrategy` with `min_available=1` (its own default) can validly have exactly"; `docs/specs/v3/layer2_registries_spec.md:1164` — "min_available: int"; `docs/specs/v3/layer2_registries_spec.md:1180-1181` — "a smaller value is an explicit partial-availability policy. There is no default that lets one surviving input silently speak for the rest."
- **Owner:** Layer 1 — the example restates a Layer-2 field incorrectly; Layer 2 owns the strategy.
- **Defect:** Layer 1 states that `min_available` defaults to 1; Layer 2 declares it mandatory with no default and explicitly rules out a default that lets one input speak for the rest.
- **Proposed direction:** Rephrase the example as "a `UnanimityStrategy` explicitly configured with `min_available=1`".
- **Confidence:** high
- **Verification:** pending

### F-L1-02 — `importance` (`OBSERVE`/`SUGGEST`/`ASSERT`) on `InferenceSignal` is defined nowhere

- **Category / severity:** R / P3
- **Locations:** `docs/specs/v3/layer1_substrate_spec.md:680-683` — "**`importance`** (`OBSERVE`/`SUGGEST`/`ASSERT`) decorates how a specific consumer *uses* a fact (e.g. Layer 3's `InferenceSignal` wrapper) ... It lives on the consuming wrapper, never on `Provenance` itself."; `docs/specs/v3/layer3_learning_spec.md:3369-3371` — "Every instance carries its subject `Location`, learner/model and artifact identity, definition fingerprint, selected tier or model context where applicable, confidence/uncertainty, `evidence_through`, and an explicit expiry."
- **Owner:** Layer 1 — it attributes a field to a Layer-3 type that Layer 3 does not define.
- **Defect:** No authoritative layer defines `importance` or the `OBSERVE`/`SUGGEST`/`ASSERT` vocabulary (the only other occurrence of "importance" in the layer specs, Layer 3 line 2438, is unrelated prose); Layer 3's exhaustive list of `InferenceSignal` contents has no such field.
- **Proposed direction:** Drop the `importance` bullet or restate it without naming a field that Layer 3 does not define.
- **Confidence:** high
- **Verification:** pending

### F-L1-04 — §8 attributes analysis-run correlation ids to "learned facts", which Layer 0 and Layer 3 do not produce

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer1_substrate_spec.md:1028-1029` — "one per evaluation cycle for same-cycle facts, one per Layer 3 analysis run for learned facts, and so on."; `docs/specs/v3/layer1_substrate_spec.md:241-242` — "new fact types are added routinely (a new `Sensor` registration, a new learned pattern)"; `docs/specs/v3/layer0_runtime_spec.md:2115-2116` — "so it mints its own fresh `correlation_id` for whatever `LearnedPattern`/`LearningProposalCandidate` it produces."; `docs/specs/v3/layer3_learning_spec.md:50-52` — "**Results are not house facts by default.** Artifacts, `ResultEnvelope`, `InferenceSignal`, and `LearningProposalCandidate` retain their typed Layer-3 lifecycle; they are never inserted into Layer 0 fact history"
- **Owner:** Layer 1 — its §8 restatement of Layer 0 §5.2 and its §3 example drifted from the "results are not facts" rule it states itself in §2.2.
- **Defect:** Layer 1's own §2.2 table and Layer 3 §2 say learning output is never a `HouseFact`; a fact derived from a signal is produced by a Layer-4 resolver in an evaluation cycle and carries that cycle's id (Layer 0 §5.2). There is therefore no "learned fact" carrying an analysis-run id, and a learned pattern does not add a fact type.
- **Proposed direction:** Restate §8 as "one per Layer-3 analysis run for its learning outputs (not facts)" and drop "a new learned pattern" from the §3 example.
- **Confidence:** medium
- **Verification:** pending

## Observations (not findings)

- §5 (lines 751–754) justifies `Location(scope="rooms")` mainly by "a learned pattern found to hold
  across a specific pair of rooms"; under §2.2 and Layer 3 §2 such a result is not a `HouseFact`. The
  scope may still be needed (e.g. Layer 5 follow-up subjects), but the motivating example is stale.
- Layer 0 §4.5 line 1352 says "Records are bounded `PersistedProjection`s (Layer 1 §4)" for
  `NotificationDeliveryRecord`, a dataclass, while Layer 1 line 408 says `PersistedProjection`
  "admits no frozen dataclass". Probably the record's serialized form is meant; left to unit X1.
- Layer 1 line 251–252 reserves `occupancy.evidence.<kind>.<sensor_id>` "for room-occupancy
  evidence", while Layer 2 §2.8.1 (line 387–388) also generates
  `occupancy.evidence.person.<ha_person_id>` at `casa`. Layer 2 line 160 admits the shape at casa,
  so the Layer-1 wording is only narrower; left to unit X4.
- §4.2 forbids any confidence not produced by the three helpers or inheritance (acceptance line
  1082), while §4.2 itself (line 612) and Layer 2 `Sensor.reliability` allow a declared non-1.0
  raw-sensor confidence. It reads as a declared constant rather than a computed formula, so it is
  not recorded as a contradiction.
