## Findings

### F-X9-01 — Layer-6 `HouseEndpoint`s are administrator-configured generation records, but Layer 8 has no editable kind for them

- **Category / severity:** O / P1
- **Locations:** `docs/specs/v3/layer6_notification_spec.md:572` — "house_endpoints: tuple[HouseEndpoint, ...]             # canonical endpoint_id order (CA4-124)";
  `docs/specs/v3/layer6_notification_spec.md:579` — "endpoint_id: str                  # stable, administrator-chosen, e.g. \"guest_room_tablet\"";
  `docs/specs/v3/layer6_notification_spec.md:176-177` — "`house` (CA4-124) is whoever is in the house and is not addressed as a person: every configured `HouseEndpoint` (a device account such as the guest-room tablet)";
  `docs/specs/v3/layer8_administration_spec.md:288-289` — "Editable object kinds, closed per owning layer";
  `docs/specs/v3/layer8_administration_spec.md:298` — "| `layer6` | `recipient`, `family_options` |";
  `docs/specs/v3/layer8_administration_spec.md:127` — "| Notifications | admin | Who receives what? | Recipients, family options, each recipient's preferences, notification history (Layer 6) |".
- **Owner:** Layer 8 §6.2 (closed kind table) and §5 Notifications; Layer 0 §4.7's Layer-6 list
  ("notification recipients and family options") has the same omission.
- **Defect:** An administrator wants the guest-room tablet to receive on-site advisories (the Layer 6
  §14 CA4-124 criterion). Layer 6 stages it as a `HouseEndpoint` in the Layer-6 generation, but every
  configuration edit must be a `ConfigurationEdit` whose `object_kind` is in Layer 8's closed table,
  which for `layer6` admits only `recipient` and `family_options`; no panel path can create, change or
  remove a house endpoint.
- **Proposed direction:** Add a `house_endpoint` kind to the `layer6` row and to the Notifications
  section, and name house endpoints in Layer 0 §4.7's Layer-6 list.
- **Confidence:** high
- **Verification:** pending

### F-X9-02 — Layer-3 artifact lifecycle transitions (shadow, `proposal_eligible`, rollback, disablement) have no Layer-8 command

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer3_learning_spec.md:1822` — "A review-only proposal type may enter shadow first, or may become `proposal_eligible` through an explicit administrative transition after offline validation.";
  `docs/specs/v3/layer3_learning_spec.md:1844-1845` — "Promotion, continued shadowing, rollback and disablement are explicit administrative generation transitions.";
  `docs/specs/v3/layer8_administration_spec.md:957` — "| `learning/promote_signal`, `learning/adopt_signal_artifact`, `learning/set_signal_adoption_mode` | command | admin | Layer 3 §4.9 (initial `live_signal_eligible` promotion, `adopt_pinned_signal_artifact`, `set_signal_artifact_adoption_mode`) |";
  `docs/specs/v3/layer8_administration_spec.md:125` — "| Learning | admin | What is it learning? | Learning definitions and family enablement, artifacts, findings, live-signal promotion and adoption (Layer 3) |".
- **Owner:** Layer 8 §5 and §13, which must offer every administrative transition Layer 3 requires
  (Layer 3 may also need to name the command, see F-L3a-03).
- **Defect:** A proposal-producing learner with `required_before_proposal` or
  `optional_before_proposal` must be moved into `shadow` and then to `proposal_eligible` by an
  administrative transition before any Layer-5 proposal exists. The only Layer-3 commands in the
  Layer-8 catalog cover live-signal promotion and adoption; no command or change-set kind enters
  shadow, promotes to `proposal_eligible`, rolls back or disables an artifact, so a proposal family
  cannot reach review through the panel. Whether these are immediate actions (Layer 0 §4.7, Layer 3
  §4.9) or generation changes (F-L3a-03), Layer 8 names neither path.
- **Proposed direction:** Add Layer-8 commands (or a defined change-set path, once F-L3a-03 is
  settled) for shadow entry, `proposal_eligible` promotion, rollback and disablement, with their
  Layer-3 owner path.
- **Confidence:** medium
- **Verification:** pending

### F-X9-03 — The map-card house banner has no owner hand-off: Layer 6 does not give Layer 8 the open `house` items

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer8_administration_spec.md:782-786` — "**House banner (CA4-124).** The card shows the open items of the Layer-6 `house` audience (Layer 6 §5.2) [...] it disappears when its item closes.";
  `docs/specs/v3/layer8_administration_spec.md:967` — "live updates of §10.3, map layout revisions and the house banner (§9.14), role-filtered";
  `docs/specs/v3/layer8_administration_spec.md:855-857` — "Layer 8 keeps them in in-memory projections fed by typed changes their owners already produce off the hot path, handed read-only to Layer 8 as an additional consumer";
  `docs/specs/v3/layer6_notification_spec.md:176-179` — "every configured `HouseEndpoint` [...] and the Heima map card's banner (Layer 8 §9.14)";
  `docs/specs/v3/layer6_notification_spec.md:308` — "`house` delivery is never digested: the map card shows open items";
  `docs/specs/v3/layer5_action_reactions_spec.md:2507-2509` — "When it is `True`, Layer 6 also delivers that item to the `house` audience (device endpoints, the map card and guests during a stay, Layer 6 §5.2)".
- **Owner:** Layer 6 (§7.2 defines delivery only through `notify.*` endpoints) and Layer 8 §10.3
  (its projection table).
- **Defect:** A `safety.weather_protection` action notice with `house_delivery=True` must appear on
  the guest-room card (Layer 6 §14). Layer 6 §7.2 delivers only by calling `notify.*` services, and
  no Layer-6 or Layer-5 text hands open `house` items to Layer 8; Layer 8 §10.3 lists only the
  automation-state, pending-items and health projections, none fed by `house` items. The banner
  therefore has no defined source, and "disappears when its item closes" has no closing event for
  Layer 8 to observe.
- **Proposed direction:** Have Layer 6 hand each `house` item phase read-only to a Layer-8
  house-banner projection, and add that projection to Layer 8 §10.3.
- **Confidence:** medium
- **Verification:** pending

### F-X9-04 — Layer 8 gives a guest no role, but a guest who is an HA administrator is an administrator for Layer 0 and for Layer 8's own role rule

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer8_administration_spec.md:76` — "`administrator` — the HA user is an HA administrator;";
  `docs/specs/v3/layer8_administration_spec.md:82-83` — "A guest, and a device account with no `Person` (a guest-room tablet), has no role.";
  `docs/specs/v3/layer0_runtime_spec.md:1838-1840` — "Learning evidence and household authority (consent, request answers, advisory feedback) read the household role; Heima configuration reads the administrator flag.";
  `docs/specs/v3/layer0_runtime_spec.md:2086-2087` — "A guest or a user with no `Person` is admitted only through `\"admin\"` when it is an HA administrator.".
- **Owner:** Layer 8 §4 (and the §16 people-and-roles criterion), which restates the axes.
- **Defect:** An HA user linked to a `Person(guest)` has HA's administrator flag. By Layer 0 the
  configuration axis reads only the administrator flag, and the ingress admits that user as `admin`;
  by Layer 8 §4 the same user is an `administrator` under the first role rule and has no role under
  "A guest [...] has no role", so the panel cannot both show and hide the administrator sections for
  that user.
- **Proposed direction:** Restate the no-role sentence as applying to a guest or device account that
  is not an HA administrator, matching Layer 0 §5.
- **Confidence:** medium
- **Verification:** pending

### F-X9-05 — Layer 5 says Layer 8 sends "only these" seven commands, but Layer 8 also submits rename, removal and restore of Reactions, including learner-origin ones

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer5_action_reactions_spec.md:1800-1801` — "Layer 8 renders descriptor-specific forms but sends only these shared typed Reaction commands to Layer 5.";
  `docs/specs/v3/layer5_action_reactions_spec.md:1830-1832` — "A learner-origin Reaction cannot be edited through this command; the unchanged-configuration revalidation of §4.2 is a separate Layer-5 staging contribution available to both origins.";
  `docs/specs/v3/layer5_action_reactions_spec.md:1757-1761` — "Restoring a removed Reaction (Layer 8 §7) appends a successor configuration generation to the same root with the restored canonical configuration and a catalog entry [...] for a learner-origin Reaction the configuration must equal a committed one";
  `docs/specs/v3/layer8_administration_spec.md:297` — "| `layer5` | `reaction` (admin-direct configuration; `display_name`, removal or unchanged-configuration revalidation for any Reaction), `guard_profile`, `comfort_trajectory_prerequisite` |";
  `docs/specs/v3/layer8_administration_spec.md:407-409` — "The result is a new generation. Restore covers configuration only: a restored Reaction returns as a new generation of the same Reaction root in `notification_only`".
- **Owner:** Layer 5 §4.2 (the closed command surface), with Layer 8 §6.2 for the restore case.
- **Defect:** An administrator restores a removed learner-origin Reaction from History. The edit is
  neither command 1 (which rejects learner-origin Reactions) nor revalidation (an unchanged current
  configuration), and Layer 8's `reaction` kind admits only admin-direct configuration, rename,
  removal and revalidation; yet Layer 5 §4.2 and Layer 8 §7 both require restore to work. Rename and
  removal are likewise catalog-entry edits that no numbered command covers, contrary to "only these".
- **Proposed direction:** Name the catalog-entry edits (rename, removal, restore) and revalidation as
  Layer-5 staging contributions in §4.2's command surface, and list restore in Layer 8's `reaction`
  kind.
- **Confidence:** medium
- **Verification:** pending

## Observations (not findings)

- `reaction.action_notice` has a single delivered phase and no closing phase (Layer 6 §4.2), so for a
  `house` action notice the banner's "disappears when its item closes" (Layer 8 §9.14) has no
  defined end.
- Layer 0 reserves `admin_command` for facts and `ApplyStep`s "of an admin-panel command", but no
  Layer-8 command produces a fact or an `ApplyStep`; the kind has no Initial-V3 producer.
- Layer 5 §7.1.1 says the panel "may expose" a read-only shadow view for the comfort trajectory;
  Layer 8 names no shadow view (optional, so not a finding).
- Layer 3 §6.1.1 allows `acknowledged` or `dismissed` finding view state; Layer 8 offers only
  acknowledgement (optional, so not a finding).
