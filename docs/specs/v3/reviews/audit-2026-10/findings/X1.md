### F-X1-01 — Recovery-target snapshots and outbox records are declared `PersistedProjection`s but cannot satisfy its depth and no-dataclass rule

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:824` — "notification delivery outbox, recovery-target snapshot, and checkpoint retain only complete `HouseFact`s or their explicitly declared normalized projections. Every such non-fact projection is a Layer-1 `PersistedProjection`: copied JSON-compatible data, maximum nesting depth 2"; `docs/specs/v3/layer0_runtime_spec.md:2598` — "facets: tuple[RecoveryFacetBaseline, ...] # non-empty; one entry per canonical facet" (with `RecoveryFacetBaseline.value: EvidenceValue`, line 2584); `docs/specs/v3/layer0_runtime_spec.md:2631` — "The coalesced snapshot is validated against the channel's closed target contract and Layer-1 projection bound"; `docs/specs/v3/layer0_runtime_spec.md:1352` — "Records are bounded `PersistedProjection`s (Layer 1 §4)" (for the frozen dataclass `NotificationDeliveryRecord`, whose field is `intent: PersistedProjection | None`, line 1326); `docs/specs/v3/layer1_substrate_spec.md:407-409` — "(for example, one recovery target) ... It admits no frozen dataclass or arbitrary object: it is a JSON mapping whose values obey the ordinary `EvidenceValue` rule, have maximum nesting depth 2"; `docs/specs/v3/layer1_substrate_spec.md:160-161` — "every enclosing list, mapping or normalized frozen-dataclass field object adds 1"
- **Owner:** Layer 0 — it chose the record shapes and declared them to be `PersistedProjection`s; Layer 1's contract is generic.
- **Defect:** A `RecoveryTargetSnapshot` normalizes to a top mapping (depth 1) holding the `facets` list (depth 2) of facet mappings (depth 3), each with an `EvidenceValue` that may itself be a collection; even a one-facet scalar target is depth 3, so every valid snapshot fails the depth-two `PersistedProjection` check that Layer 0 §4.1 and §7.4 apply to it. Likewise a `NotificationDeliveryRecord` is a frozen dataclass, which `PersistedProjection` does not admit, and nesting its `intent` (itself up to depth 2) inside the record yields depth 3. The Layer-1 L1 pass left this case to X1.
- **Proposed direction:** Either define the snapshot and record serialization so that each retained projection is depth two (as done for hold maps with canonical JSON text), or state that only the producer-owned payload (`intent`, each facet value) is a `PersistedProjection` and the record envelope is a separately bounded storage shape.
- **Confidence:** high
- **Verification:** pending

### F-X1-02 — A calendar Sensor reads Layer 0's `active_now` directly, which Layer 0 neither registers nor permits

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer2_registries_spec.md:694-696` — "`CalendarWindowReadBinding` reads only the raw windows active **now** for one `calendar.*` entity through Layer 0's `active_now` view (§3.4.1 of the Layer 0 spec)"; `docs/specs/v3/layer0_runtime_spec.md:883-884` — "A Layer-5 plan or a core Layer-2 declared-context producer (Layer 2 §2.9) that needs calendar context declares a finite `CalendarViewRequirement` during staging: one permitted `calendar.*` entity and one positive bounded upcoming horizon"; `docs/specs/v3/layer0_runtime_spec.md:460` — "Consumers declare their largest upcoming horizon at registration."; `docs/specs/v3/layer0_runtime_spec.md:3475` — "an undeclared requirement, wider horizon or direct provider/cache read is rejected"
- **Owner:** Layer 0 and Layer 2 jointly; Layer 0 enumerates who may read calendar context and Layer 2 defines the Sensor read path.
- **Defect:** A registered `Sensor` with `CalendarWindowReadBinding` (for example the calendar-derived workday Sensor of Layer 2 §5.1) is neither a Layer-5 plan nor the declared-context producer, so it has no `CalendarViewRequirement` and no declared horizon; its "`active_now` view" read is a direct cache read, which the Layer-0 criterion rejects. Under Layer 0 as written, the Sensor either has no cached timeline for its entity or performs a forbidden read.
- **Proposed direction:** Add calendar Sensors to Layer 0's list of requirement declarers (with the minimum positive horizon used by `household.guest_stay`) and route their read through the frozen view, or name the Sensor `active_now` read as an allowed exception in Layer 0 §3.4.1/§4.1 and §13.
- **Confidence:** medium
- **Verification:** pending

### F-X1-03 — Layer 2 hands Layer 0 an "entity delta" that deletes recovery snapshots; Layer 0 §7.4 has no such input or rule

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer2_registries_spec.md:278-282` — "Removal of an Actuator, or a changed `entity_id` for the same stable `actuator_id`, also deletes the old endpoint's per-channel snapshots; they are never migrated to another HA endpoint merely because the logical id stayed the same. Layer 0 receives this resolved policy/fingerprint/entity delta at composition commit"; `docs/specs/v3/layer0_runtime_spec.md:2655-2657` — "At configuration-generation cutover (Layer 2 §2.5), Layer 0 receives resolved Actuator policy and fingerprint deltas rather than reading a registry. A snapshot whose recorded fingerprint or recovery policy differs from the active candidate is discarded; `policy=\"never\"` deletes it."
- **Owner:** Layer 0 — Layer 2 states an obligation on the checkpoint owner that Layer 0 §7.4 does not honor.
- **Defect:** Layer 0 receives and acts on only policy and fingerprint deltas. Layer 2's word "also" makes Actuator removal and an `entity_id` rebinding separate deletion triggers, but the Actuator semantic fingerprint's fields are not defined, and for a removed Actuator there is no "active candidate" to compare. A snapshot of a rebound or removed endpoint may therefore survive in Layer 0 and be exposed as a recovery baseline, which Layer 2 says must never happen.
- **Proposed direction:** Make Layer 0 §7.4 accept the entity/removal delta and state that removal or a changed `entity_id` deletes the channel snapshots, or state in Layer 2 that `entity_id` is part of the Actuator execution semantic fingerprint and that removal discards snapshots.
- **Confidence:** medium
- **Verification:** pending

### F-X1-06 — `FactSource.source_id` example "an entity id" conflicts with Layer 2's Sensor `source_id`

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:1730` — "source_id: str # stable id within that kind, e.g. an entity id, an analyzer id, a reaction id"; `docs/specs/v3/layer2_registries_spec.md:2292` — "`source_id` is the `sensor_id`/`fusion_id`"; `docs/specs/v3/layer2_registries_spec.md:554` — "sensor_id: str # stable Heima logical-reading id, not an HA entity_id"
- **Owner:** Layer 0 — its example names an identifier that the only direct-read producer (Layer 2 `Sensor`) deliberately does not use.
- **Defect:** For `kind="sensor"`, Layer 0's example suggests an HA entity id as `source_id`, while Layer 2 fixes it to the stable `sensor_id` so that an HA rename or re-pair preserves history; `source_id` is part of `FactSourceFingerprint`, so following the Layer-0 example would make an entity rename a state change and break the Layer-2 identity rule.
- **Proposed direction:** Change the Layer-0 example to "a Sensor or Fusion registry id".
- **Confidence:** medium
- **Verification:** pending

## Observations

- Layer 2 §2.5 and §9 require a "force-write" of every retained impacted producer "with its new
  configuration fingerprint", including transitive Fusion dependents; Layer 0 §4.2 has no
  generation-cutover force-write exception and relies on a changed fingerprint. Whether a
  transitively impacted rule's own execution semantic fingerprint changes is not defined, so it is
  unclear whether this is ordinary write-on-change or a third forced-write case.
- Layer 2 §2.5 emits "one terminal `available=False` state fact for each removed or relocated
  producer claim"; Layer 0 §4 does not say under which generation's claim that last fact is
  admitted when the new generation no longer contains the claim.
- The core-generated declared-context facts (Layer 2 §2.9) are produced by neither a `Sensor` nor a
  `FusionRule`; neither layer assigns their `FactSource.kind`, and Layer 0 §4.1/§10.1 does not name
  the durable store of panel declarations that "survive a restart".
- `FactTypeClaim.owner_id` for Layer-2 registrations is not specified; if it were per producer,
  two Sensors with the same `fact_type` at different Locations would overlap with differing owners
  and be rejected by Layer 0 §4, contrary to Layer 2 §2.3.
- Layer 2 §7 allows a `LearnedWindow` in `FusionRule.stability`, and Layer 0 §3.2 leaves its
  calibration to "whichever ... `FusionRule` uses" it, but no Fusion calibration path exists that
  respects Layer 2 §2.2's no-I/O rule.
- Layer 2 §5.2 runs a dwell deadline as a "targeted evaluation of that fusion and its current-cycle
  dependents"; Layer 0 §3.5/§4.1 define cycle instants and `PreviousCycleSnapshot` sealing only for
  full evaluation cycles.
