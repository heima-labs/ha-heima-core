## Findings

### F-L8-01 — Consent-authority change is an immediate action, but Person removal requires it in the same change set

- **Category / severity:** C / P1
- **Locations:** `docs/specs/v3/layer8_administration_spec.md:258-264` — "**Immediate actions** are
  governance or answer commands that are not configuration mutations: promotion, disablement,
  consent grant or revoke, consent-authority changes, proposal review, [...] They take effect at
  once after a confirmation dialog that states their consequence, and never enter the change set.";
  `docs/specs/v3/layer8_administration_spec.md:959` — "| `consent_authority/stage` | command | admin |
  Layer 5 §4.2 |"; `docs/specs/v3/layer5_action_reactions_spec.md:3970-3973` — "Removing or
  reclassifying a referenced Person is an authority removal: the same change set must carry the
  authority change with one disposition per current consent that person granted (§4.2 command 7), or
  it is rejected."; `docs/specs/v3/layer2_registries_spec.md:2352-2353` — "Reclassifying a
  `resident` who is in `HouseholdConsentAuthority` to `guest` without the authority disposition in the
  same change set is rejected (Layer 5 §7.1.1)."; `docs/specs/v3/layer5_action_reactions_spec.md:1805`
  — "Commands 2 to 7 are immediate actions".
- **Owner:** Layer 8 (§6.1, §6.2 kind table, §13), together with Layer 5, whose own command list
  classifies command 7 as immediate while §7.1.1 requires it inside a change set.
- **Defect:** An administrator reclassifies a consent-authorized resident to `guest` (a `layer2`
  `person` edit in the change set). Layer 2 and Layer 5 §7.1.1 reject the change set unless it carries
  the authority change with dispositions; Layer 8 offers the authority change only as an immediate
  `consent_authority/stage` command that "never enter[s] the change set", and the §6.2 kind table has
  no `layer5` kind for it. Issuing the authority change first is a separate commit, so the two rules
  cannot both hold for this case and the reclassification has no valid path as specified.
- **Proposed direction:** Decide whether consent-authority changes are change-set edits (add a
  `layer5` kind) or immediate commands, and align Layer 8 §6.1/§6.2/§13, Layer 5 §4.2 command 7 and
  §7.1.1, and Layer 2 §2.8 to that single rule.
- **Confidence:** high
- **Verification:** pending

### F-L8-02 — `extension_requirement` suggestions are computed from the active generation, where an instance with a missing producer cannot exist

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer8_administration_spec.md:365-367` — "`suggestions/list` is a
  slow-path query over the active generation and HA's area, floor, label, device and entity registries
  and current state objects."; `docs/specs/v3/layer8_administration_spec.md:1150-1152` — "An instance
  whose slot key has no producer shows an `extension_requirement` suggestion that opens a prefilled
  Sensor form and disappears once the key is produced."; `docs/specs/v3/layer7_extensions_spec.md:132-135`
  — "If no registered producer provides that exact key with a compatible value contract, the instance
  fails validation; Layer 8 turns the missing key into a suggestion to create a `Sensor` (CA4-131).";
  `docs/specs/v3/layer7_extensions_spec.md:358-359` — "An instance whose slot key has no compatible
  producer fails validation and yields one missing-key requirement; creating the Sensor makes it
  validate."
- **Owner:** Layer 8 §6.5, which defines where suggestions are computed.
- **Defect:** An administrator adds an instance whose input slot has no producer. Layer 7 says the
  instance fails validation and Layer 8 turns the missing key into a suggestion; but such an instance
  never commits, so it is absent from the active generation, and §6.5 computes suggestions only over
  the active generation. The `extension_requirement` suggestion of §6.5 and the §16 criterion can
  therefore never appear for the creation case Layer 7 describes (the missing key surfaces only as a
  staging error).
- **Proposed direction:** State that `extension_requirement` suggestions are also derived from the
  open change set's staging errors (or from the candidate composition), or restate Layer 7 §4/§13
  to match the active-generation-only rule.
- **Confidence:** medium
- **Verification:** pending

### F-L8-03 — Finding acknowledgement is called installation-wide; Layer 3 limits it to the acknowledging administrator

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer8_administration_spec.md:379-380` — "**Dismissing** records the
  `SuggestionKey` as Layer-8 view state, like finding acknowledgement: installation-wide, stored with
  HA's storage helper, never part of the composed generation."; `docs/specs/v3/layer3_learning_spec.md:3274-3276`
  — "The administrative surface may separately record `acknowledged` or `dismissed` view/audit state
  for a stable finding identity, including historic records. Such state can alter only that
  administrator's presentation or filtering".
- **Owner:** Layer 8 §6.5 (the restatement), or Layer 3 §6.1.1 if installation-wide is intended.
- **Defect:** With two administrators, administrator A acknowledges a finding. Per Layer 3 only A's
  presentation changes; per Layer 8 ("like finding acknowledgement: installation-wide") B's view
  changes too.
- **Proposed direction:** Align the scope of finding-acknowledgement view state in one of the two
  texts.
- **Confidence:** medium
- **Verification:** pending

### F-L8-05 — §7 defines what residents see in history, but history is administrator-only

- **Category / severity:** C / P3
- **Locations:** `docs/specs/v3/layer8_administration_spec.md:399-402` — "An administrator who is also
  a resident sees the actor's HA display name; a resident sees names only for their own actions and the
  actor's role otherwise [...] Guests and device accounts have no history."; `docs/specs/v3/layer8_administration_spec.md:128`
  — "| System | admin | Is Heima healthy? | Health, diagnostics, holds (read-only), recovery, history
  (§7) |"; `docs/specs/v3/layer8_administration_spec.md:947` — "| `history/list`, `history/diff` |
  query | admin |".
- **Owner:** Layer 8 (§7 or §5/§13), whichever is wrong about resident access.
- **Defect:** A resident who is not an administrator has no section or query that returns history
  (System and `history/list` are admin-only), so the §7 rule for what a resident sees cannot apply;
  conversely, if residents do see history, the §13 role check rejects their `history/list` call.
- **Proposed direction:** Either name the resident surface and query that shows history slices, or
  drop the resident-viewer rule from §7.
- **Confidence:** medium
- **Verification:** pending

### F-L8-06 — Up-direction change clears placements on every floor (§9.1, §9.4) or on one floor (§16)

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer8_administration_spec.md:476` — "One direction is at the top of the
  map for the whole installation (§9.4)."; `docs/specs/v3/layer8_administration_spec.md:563-565` —
  "Changing the up direction clears the floor placements, after a warning in the editor, because every
  opening changes side."; `docs/specs/v3/layer8_administration_spec.md:1082-1083` — "Changing the up
  direction clears that floor's placements only after the editor's warning."
- **Owner:** Layer 8 §16 (acceptance criterion), or §9.4 if per-floor clearing is intended.
- **Defect:** In a two-floor house, changing the installation-wide up direction while editing floor 0:
  §9.4's reason ("every opening changes side") applies to both floors, so both floors' placements
  should clear; §16 tests that only "that floor's" placements clear, leaving floor 1 pinned in the old
  orientation.
- **Proposed direction:** State explicitly in §9.4 whether all floors' placements clear and make §16
  test the same.
- **Confidence:** medium
- **Verification:** pending

### F-L8-07 — Redaction keeps Heima ids, but a Heima `recipient_id` is administrator-chosen and may be a person's name

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer8_administration_spec.md:1000-1003` — "**Redaction.** Person names,
  HA user ids, notification recipient targets (phone numbers, email addresses, notify targets),
  coordinates and every secret are replaced by a pseudonym [...] Heima ids and HA `entity_id`s stay,
  because debugging needs them."; `docs/specs/v3/layer6_notification_spec.md:154` — "recipient_id: str
  # stable, administrator-chosen, e.g. \"stefano\"".
- **Owner:** Layer 8 §14.1 (redaction rule), or Layer 6 §5.1 if `recipient_id` must not carry a name.
- **Defect:** The diagnostics file includes the full active configuration (§14.1 "Content"), hence
  Layer 6 recipients. With `recipient_id="stefano"`, the rule "Heima ids [...] stay" keeps the person's
  name in clear while "Person names [...] are replaced by a pseudonym" requires it redacted; both
  cannot hold.
- **Proposed direction:** Pseudonymize `recipient_id` (and any other administrator-chosen id that may
  carry personal data) in §14.1, or constrain such ids in their owner layer.
- **Confidence:** medium
- **Verification:** pending
