### F-L6-01 — `safety.posture_check` advisories are declared `safety` but `reaction.advisory` has the fixed family `suggestion`

- **Category / severity:** C / P1
- **Locations:** `docs/specs/v3/layer6_notification_spec.md:102` — "| `reaction.advisory` | `ReactionAdvisoryOccurrence` (Layer 5 §6.0) | residents, house (when `house_delivery`) | suggestion | info |"; `docs/specs/v3/layer6_notification_spec.md:243-246` — "For the three kinds that report on a Reaction's action — `reaction.follow_up`, `automation.availability` and `reaction.action_notice` — the family comes from the namespace of that Reaction's descriptor"; `docs/specs/v3/layer6_notification_spec.md:253-255` — "So a window held open while weather protection is active, a weather-protection step left unconfirmed, the weather-protection action notice and every `safety.posture_check` advisory (Layer 5 §7.5) are all `safety` notices."; `docs/specs/v3/layer5_action_reactions_spec.md:4408-4410` — "Its namespace places its advisories in the `safety` notification family (Layer 6 §6.1): they are delivered immediately, quiet hours included, to residents only."; `docs/specs/v3/layer6_notification_spec.md:275` — "| `suggestion` | held; one end-of-quiet-hours digest of the still-open advisories (§6.4) | none |"
- **Owner:** Layer 6 — its kind table and §6.1 scope decide the family; the namespace rule excludes `reaction.advisory`, and `ReactionAdvisoryOccurrence` (Layer 5 §6.0, lines 2468–2488) carries no `reaction_descriptor_id` from which a namespace could be read.
- **Defect:** a `safety.posture_check` advisory (e.g. `entry_unlocked_while_empty`) opened at night is, by §4.2/§6.1 scope, a `suggestion`: held and digested at the end of quiet hours (and subject to personal `off`); by §6.1 line 254 and Layer 5 §7.5 it is `safety`: delivered immediately and never filtered.
- **Proposed direction:** make `reaction.advisory`'s family descriptor-derived (adding `reaction_descriptor_id` to the advisory occurrence) or drop the `safety` claim for posture-check advisories in both layers.
- **Confidence:** high
- **Verification:** pending

### F-L6-02 — Per-proposal `closed` clearing contradicts the shared digest tag

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer6_notification_spec.md:544-546` — "Closing phases (`closed` of an advisory, consent request or proposal) append their audit fact, retire any undelivered opening record of the same item, and apply §7.4 clearing when the opening phase was delivered."; `docs/specs/v3/layer6_notification_spec.md:379` — "| `proposal.review_pending` | one fixed digest tag per audience |"; `docs/specs/v3/layer6_notification_spec.md:301-302` — "All digests use one fixed tag per audience, so a new digest replaces the previous one on the phone. When no proposal remains open, Layer 6 sends `clear_notification` on that tag."
- **Owner:** Layer 6 §9.3 — it applies the generic per-item clearing to proposals, whose item tag is the shared digest tag.
- **Defect:** two proposals delivered in one digest; one is approved (`closed`). §9.3 applies §7.4 clearing on the item tag, i.e. the shared digest tag, removing the digest from every administrator's phone while the other proposal is still open; §6.3 clears only when no proposal remains open. (The §4.2 row also lists no clearing phase for `proposal.review_pending`.)
- **Proposed direction:** exclude proposals from §9.3's clearing sentence and refer to §6.3's "no proposal remains open" rule.
- **Confidence:** high
- **Verification:** pending

### F-L6-03 — The "open request with buttons is never filtered or silenced" rule also covers advisories, emptying the `suggestion` preferences

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer6_notification_spec.md:222-224` — "A phase with answer buttons whose request is still open (a consent request, a recovery confirmation) reaches the person whatever the family level (CA4-77)"; `docs/specs/v3/layer6_notification_spec.md:279-282` — "A phase with answer buttons whose request is still open (a recovery confirmation, a consent request) is never silenced"; `docs/specs/v3/layer6_notification_spec.md:102` — "`opened` (`closed` clears) | `layer5.advisory_feedback`: done / dismiss / not_useful"; `docs/specs/v3/layer5_action_reactions_spec.md:2630-2632` — "the owner `layer5.advisory_feedback` declares a request ... with actions `done`, `dismiss` and `not_useful` ... open for as long as the activation lasts"; `docs/specs/v3/layer6_notification_spec.md:219-220` — "`off` excludes this person from that family at all times"; `docs/specs/v3/layer6_notification_spec.md:287-288` — "For `suggestion`, `quiet_silent` excludes the person from the end-of-quiet-hours digest."
- **Owner:** Layer 6 §5.4/§6.2 — the rule is stated by predicate, and the parenthetical lists are examples, not a closed scope.
- **Defect:** an `opened` advisory is a phase with answer buttons whose request is open until the activation closes, so by the predicate it reaches a resident who set `suggestion` to `off` or `quiet_silent`; `reaction.advisory` is the only `suggestion` kind, so those personal levels would never take effect, contradicting their definitions (and §6.4's held digest).
- **Proposed direction:** restrict the rule to the closed list of kinds (consent request, recovery confirmation) instead of "a phase with answer buttons".
- **Confidence:** medium
- **Verification:** pending

## Observations

- §3 (lines 53–54) states each accepted phase appends exactly one fact with its `ready` record; §11 (lines 610–612) carves out a memory-only `system.health` delivery without a fact. Layer 0 §4.5 allows best-effort delivery on storage failure, so this is a qualification gap in the principle, not a defect.
- §7.3 (line 363) defines fallback text only "for residents" or "for administrators"; the `consent_authorities` audience has no stated wording.
- §7.4 (lines 386–387) "after a restart, to every recipient of the audience, since that record is in memory" reads as if it should say the per-recipient delivery set is only in memory.
- §7.5 (line 403) "superseded by a `reissued` phase of the same request" — a reissue carries a new request id; "same item" matches §9.3.
- §14 (line 675) "an action notice is delivered at once" holds only because Initial V3's only action-notice descriptor is `safety.weather_protection`.
- §7.3's fallback trigger "at least one resolved recipient is still unreached" does not say whether guest recipients reached through `house` count.
