## Findings

### F-L2-01 — Core-generated `presence.household` FusionRule is invalid when no resident is tracked

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer2_registries_spec.md:399-403` — "One core-generated `FusionRule` produces the boolean `presence.household` at casa from every resident evidence Sensor, with `WeightedQuorumStrategy(threshold=1.0)` (any resident home is `True`) and `min_available_weight` equal to the number of tracked residents: … With no tracked resident it is `available=False`."; `docs/specs/v3/layer2_registries_spec.md:187` — "Every `FusionRule.inputs` tuple is non-empty"; `docs/specs/v3/layer2_registries_spec.md:197-198` — "`threshold` is finite and in `(0, total_configured_weight]`"
- **Owner:** Layer 2 §2.8.1, which defines the generated rule without saying what happens when it would have no inputs.
- **Defect:** A household whose residents have no device tracker (or that has no resident) gives the generated rule zero inputs and total configured weight 0. §2.4 then rejects it (empty `inputs`, and `threshold=1.0` is outside `(0, 0]`), so the generation fails staging. Yet §2.8.1 says the fact exists and reads `available=False` in this same case. Both rules cannot hold.
- **Proposed direction:** State whether the core skips the FusionRule and emits a fixed `available=False` claim for zero tracked residents, or exempts the generated rule from the §2.4 cardinality checks.
- **Confidence:** high
- **Verification:** pending

### F-L2-02 — Two core-generated Sensors read the same HA person state, against "one readable signal path, one owner"

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer2_registries_spec.md:387-389` — "one Sensor `occupancy.evidence.person.<ha_person_id>` at casa reads the HA person's state"; `docs/specs/v3/layer2_registries_spec.md:394-396` — "one Sensor `presence.evidence.person.<ha_person_id>` at casa reads the HA person's state with the same mapping"; `docs/specs/v3/layer2_registries_spec.md:606` — "Every Home Assistant **readable signal path** Heima cares about is registered exactly once, here"; `docs/specs/v3/layer2_registries_spec.md:958-960` — "another Sensor cannot register either reserved `sun.sun` attribute path under a second fact type because one HA readable signal path has one registered owner."
- **Owner:** Layer 2 (§2.8.1 vs §3 / §3.6): either the one-owner-per-path rule or the double registration must change.
- **Defect:** For each tracked resident, §2.8.1 generates two Sensors with a `StateReadBinding` on the same `person.*` state, each under a different fact type. §3 says each readable path is registered exactly once, and §3.6 relies on that as a staging rule ("cannot register … under a second fact type"). If the rule is enforced as §3.6 implies, the core-generated pair is rejected; if not enforced, §3.6's guarantee for `sun.sun` has no basis.
- **Proposed direction:** Either state that one-owner-per-path is a staging rule with an explicit exemption for §2.8.1, or derive the presence evidence from the same Sensor's fact instead of a second binding.
- **Confidence:** medium
- **Verification:** pending

### F-L2-03 — Physical-evidence "recipe applies equally to presence", but its validator admits only `occupancy.physical`

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer2_registries_spec.md:1684-1686` — "Its `validate_binding` permits exactly one of two homogeneous shapes: it either produces `occupancy.physical` at a room from same-room `occupancy.evidence.<kind>.<sensor_id>` inputs, or it produces `occupancy.physical` at `casa` from casa `occupancy.evidence.<kind>.<sensor_id>` inputs."; `docs/specs/v3/layer2_registries_spec.md:1747-1748` — "This recipe applies equally to occupancy, presence, or another registered physical boolean family."
- **Owner:** Layer 2 §5.3, "Fast/confirmed use of one fusion" paragraph.
- **Defect:** Staging a `physical_evidence.weighted_evidence` fusion for presence or any other physical boolean family is rejected by the formula's own `validate_binding`, which admits only the two `occupancy.physical` shapes. The recipe claims it applies to them.
- **Proposed direction:** Restrict the recipe sentence to the two admitted `occupancy.physical` shapes, or widen the validator through a reviewed formula version.
- **Confidence:** high
- **Verification:** pending

### F-L2-04 — §5.6 rationale says FusionRules are "core-team-authored only (§2.1)"; §2.1 and the rest of Layer 2 make them administrator-configured

- **Confidence:** medium
- **Verification:** pending

### F-L2-08 — The 14-day horizon "must exceed ceiling plus largest recovery", but Layer 5 allows the sum to equal 14 days

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer2_registries_spec.md:485-487` — "It reads active and upcoming calendar windows over a core-fixed horizon of **14 days**, which must exceed the ceiling of the comfort-trajectory minimum absence duration plus the largest recovery duration (Layer 5 `planned_absence_program`)"; `docs/specs/v3/layer5_action_reactions_spec.md:3654-3655` — "floor = 24 h, ceiling = 7 days"; `docs/specs/v3/layer5_action_reactions_spec.md:3662-3665` — "`end_beyond_horizon=true` means at least the 14-day Layer-2 horizon, which always exceeds the ceiling. … A parameter whose `conservative_recovery_duration` exceeds 7 days could not schedule recovery inside the horizon: the descriptor abstains"
- **Owner:** Layer 2 §2.9 (restatement of a Layer-5 bound; the rule lives in Layer 5 §7.1, not in `planned_absence_program`).
- **Defect:** Layer 5 abstains only when recovery is more than 7 days, so a 7-day recovery is admitted. Ceiling plus that recovery is 7 + 7 = 14 days, which equals the horizon instead of exceeding it. The two layers also state different invariants: Layer 2 requires horizon > ceiling + recovery, while Layer 5 only claims horizon > ceiling. The cited location is wrong too: the minimum absence duration is defined in Layer 5 §7.1, not in `planned_absence_program` (§3.2).
- **Proposed direction:** Align the two restatements on one inequality (strict or non-strict) and cite Layer 5 §7.1.
- **Confidence:** medium
- **Verification:** pending
