### F-X2-01 — Recovery classification is promised to every semantic resolver, but no Layer-4 input carries it

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:3006-3010` — "wall-clock time and Recovery's classification are **engine-computed context**, read-only input available to every semantic resolver within the current cycle, not another resolver's output. … A semantic resolver reads Layer-0 context fresh every cycle"; `docs/specs/v3/layer0_runtime_spec.md:3506` — "Recovery/Checkpoint classification is available, read-only, before the first semantic resolver runs in every test cycle"; `docs/specs/v3/layer4_domain_spec.md:199` — "An evaluator can read only declared lower-fact slots, declared upstream semantic-claim slots, one declared optional signal slot, parameters, and declared previous-cycle values."; `docs/specs/v3/layer4_domain_spec.md:204-207` — "The coordinator attaches Layer 0's opaque `FrozenHistoryView`, `FrozenCalendarView`, and `HoldAdmissionView`, plus Layer 0's `FrozenRecoveryView` … before Layer-5 evaluation."
- **Owner:** Layer 0 §11 (and its §13 criterion): Layer 4 deliberately closes the evaluator inputs and routes the frozen recovery view to Layer 5 only.
- **Defect:** `SemanticInputSnapshot` (L4 §5.1) contains the intake group, current values, fingerprints, signals, cycle identity/`when` and `previous_cycle` values, but no recovery state, and `SemanticInputSchema` has no recovery slot. A resolver that should behave conservatively during `startup_recovery` (as Layer 0 §7 intends: "available, **read-only**, to everything downstream") cannot read it under Layer 4, while Layer 0 says it can.
- **Proposed direction:** restrict Layer 0 §11 to cycle identity/time for semantic resolvers and name Layer 5 (via `FrozenRecoveryView`) as the recovery consumer, or add a declared recovery input to Layer 4.
- **Confidence:** high
- **Verification:** pending

### F-X2-02 — Live Layer-3 feature evaluation needs a frozen buffer read that Layer 0 offers only to Layer 5

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer3_learning_spec.md:472-474` — "For that usage, the same versioned feature resolver evaluates the same `SampleBinding` against the current Layer-0 snapshot and its declared bounded buffer"; `docs/specs/v3/layer3_learning_spec.md:3380-3381` — "The emitter reads only the adopted artifact and its declared bounded inputs from that frozen intake and the sealed previous-cycle values"; `docs/specs/v3/layer0_runtime_spec.md:850-852` — "**`FrozenHistoryView` is the bounded current-cycle history view for policy evaluation, not a second store.** During Layer-5 staging, every enabled `ReactionEvaluationPlan` declares its finite set of short-term `HistoryViewRequirement`s"; `docs/specs/v3/layer0_runtime_spec.md:872` — "The view has no general query API: Layer 5 may read only a declared requirement id"
- **Owner:** Layer 0 §4.1: Layer 3 relies on an in-cycle bounded-buffer read for `runtime_resolvable` features (`CausalAggregateFeature`, `CausalSequenceFeature` over a `window`), but the only frozen hot-path history view is declared by and readable by Layer 5.
- **Defect:** a live `indirect.semantic_assist.v1` emitter whose binding has a 30-minute `event_count` feature must read the short-term buffer during the cycle. Layer 0 defines no requirement declaration, freezing point or read API for that Layer-3 emitter (its buffer requirement registration only sizes retention), so the emitter either reads the mutable live buffer, which Layer 0 forbids for hot-path policy reads, or cannot compute the feature; Layer 3's own two sentences also disagree on whether the buffer is an input at all.
- **Proposed direction:** let the Layer-3 emitter declare `HistoryViewRequirement`s frozen at the same `CycleInputBarrier` (and say so in both layers), or restrict `runtime_resolvable` features to current and previous-cycle values.
- **Confidence:** medium
- **Verification:** pending

### F-X2-03 — `InferenceSignal` must carry the cycle `correlation_id`, but its closed payload has no such field

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:2109-2112` — "one `correlation_id` is minted at the start of each engine evaluation cycle and propagated to every `HouseFact` …, every `InferenceSignal` emitted in that cycle (Layer 3 §6.3) and every `ApplyStep`"; `docs/specs/v3/layer3_learning_spec.md:3369-3371` — "Every instance carries its subject `Location`, learner/model and artifact identity, definition fingerprint, selected tier or model context where applicable, confidence/uncertainty, `evidence_through`, and an explicit expiry."; `docs/specs/v3/layer3_learning_spec.md:3428-3430` — "It rejects an unknown/inactive contract, another producer or consumer, mismatched assertion, payload extension, or longer TTL."

- **Proposed direction:** add `correlation_id` to the `InferenceSignal` common fields and the closed `IndirectSemanticAssistSignal` payload, or drop signals from the Layer 0 §5.2 list.
- **Confidence:** high
- **Verification:** pending

### F-X2-04 — Layer 3's CPU-credit planner needs process CPU measurements that `RuntimeHealthSnapshot` does not contain

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer3_learning_spec.md:3014-3015` — "CPU credit accrues from elapsed monotonic time and actual process CPU time, never raw host CPU percentages."; `docs/specs/v3/layer3_learning_spec.md:3003` — "`C_slow = max(0, s * C - C_engine_baseline)`"; `docs/specs/v3/layer3_learning_spec.md:2988-2989` — "Layer 3 consumes Layer 0's immutable read-only `RuntimeHealthSnapshot` (§9), never a host-wide guess or a live HA object."; `docs/specs/v3/layer0_runtime_spec.md:2870-2874` — "It contains `captured_monotonic`, the source/capability set and last successful probe time, effective CPU capacity when known, an effective enforceable memory limit when known, current Heima process RSS when available, cgroup memory-event and CPU/memory-pressure evidence when available, plus a bounded recent distribution of completed engine cycle latency."; `docs/specs/v3/layer0_runtime_spec.md:2895-2896` — "Thus it supplies the measurement contract while Layer 3 owns every admission, capacity, and degradation decision."
- **Owner:** Layer 0 §9, which claims to supply the measurement contract: it lists no process CPU time and no engine CPU usage from which `C_engine_baseline` could be derived.
- **Defect:** the planner's `C_slow` and CPU-credit accrual depend on Heima process CPU time and an engine CPU baseline; neither is a `RuntimeHealthSnapshot` field, and Layer 3's `EngineHealthBaseline` holds only "the high-water Heima RSS and the healthy cycle-latency distribution" (l.2990-2991). The CPU side of the capacity plan therefore has no specified measurement source.
- **Proposed direction:** add process CPU time (and the engine CPU share it derives) to `RuntimeHealthSnapshot`, or state that Layer 3 measures its own process CPU time outside the snapshot.
- **Confidence:** medium
- **Verification:** pending

### F-X2-11 — Changing the learning installation profile is a configuration mutation outside the composed generation

- **Category / severity:** C / P3
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:1586-1592` — "Every configuration mutation in any layer — … a Layer-3 learning definition, … — activates only as part of one **composed configuration generation**. - **Proposed direction:** add the installation profile to Layer 0 §4.7's list of non-generation changes, or route it through a Layer-3 generation.
- **Confidence:** medium
- **Verification:** pending

## Observations

- Layer 4 §8 requires a removed or invalidated state resolver to emit "exactly one terminal
  `available=False` fact for its output claim at the swap"; Layer 0 §4.7 does not say under which
  generation's claim and `configuration_fingerprint` a fact of a producer absent from the new
  composition is appended. Missing lifecycle detail, not classified as a finding.
- Layer 3 §6.3 arms the signal-expiry `AtJob` with `basis="elapsed"`, while `expires_at` may be a
  required input's freshness deadline; Layer 0 §3.1 classifies a Layer-2 `last_reported +
  max_source_age` expiry as `wall_clock`. The cycle-instant comparison in Layer 4 §6 makes the
  elapsed basis workable; worth a sentence.
- Layer 0 §3.1 gives `owner="semantic_resolver"` as an `AtJob` owner example, while Layer 4 resolvers
  own no timer (Layer 3 owns signal expiry). Illustrative only.
