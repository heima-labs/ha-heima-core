### F-X3-01 — Layer 5 classifies a timing-model binding as breaking, but Layer 0's dependency index has no Layer-3 learning-definition producer or Layer-5 timing-model consumer

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer5_action_reactions_spec.md:1719-1723` — "When a confirmed change elsewhere makes the current generation's plan fail validation (**breaking**: a missing or changed trigger, guard, axis, history, calendar, timing-model or Actuator-channel binding, or a changed derived Topology/Actuator property it uses"; `docs/specs/v3/layer5_action_reactions_spec.md:1558-1559` — "Staging resolves the named core learning kind/version and staged definition, checks its exact fingerprint"; `docs/specs/v3/layer0_runtime_spec.md:1616-1622` — "Layer 0 builds a staging-only dependency index from those declarations: producer claims (`FactTypeClaim` and `(fact_type, Location)`) and Actuator channels on one side; every consumer reference on the other — Fusion inputs, Layer-3 `FactSlot`/`SampleBinding` sources, Layer-4 input bindings and upstream claims, Layer-5 trigger, guard, envelope-axis, history, calendar and Actuator-channel bindings, every consumer of a derived Topology or Actuator property ... and Layer-6 publication keys."
- **Owner:** Layer 0 §4.7 — it owns the dependency index and the breaking/semantic_only classification that Layer 5 §4.2 relies on.
- **Defect:** a `ReactionTimingModelBinding` depends on a staged Layer-3 learning definition, not on a fact claim or an Actuator channel. A candidate that removes or changes that learning definition has no producer entry in Layer 0's index and Layer 5's timing-model binding is not a listed consumer kind, so the commit's impact record cannot list the Reaction as `breaking`, while Layer 5 §4.2 requires that very classification to project `configuration_invalid`.
- **Proposed direction:** add Layer-3 learning definitions as producers and Layer-5 timing-model bindings as consumers in Layer 0 §4.7's index (or move the case into a Layer-5-owned dependent invalidation explicitly).
- **Confidence:** medium
- **Verification:** pending

### F-X3-02 — Layer 0 says Layer 5 supplies the recovery-confirmation proposal, subject and proposed facets; Layer 5's body defines no such hand-off

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:2699-2700` — "Layer 5 supplies the current admitted recovery proposal from §7.4; Layer 0 owns its identity, deadline and lifecycle."; `docs/specs/v3/layer0_runtime_spec.md:2772-2773` — "Layer 5 supplies the subject and the bounded proposed-facet projection together with the proposal; Layer 0 adds no Actuator lookup."; `docs/specs/v3/layer0_runtime_spec.md:2709-2710` — "proposal_fingerprint: str # canonical digest of final target, observed channel state/epoch, baseline identity and admission inputs"; `docs/specs/v3/layer5_action_reactions_spec.md:4765-4767` — "A `require_confirmation` recovery proposal uses Layer 0 §7.4.1 for one request per channel and recovery episode. Layer 5 recomputes its final target and ordinary guards from fresh cycle inputs" (acceptance criterion; the Layer-5 body mentions recovery only for the anchor at lines 3021–3031 and the authority filter at lines 1519–1520).
- **Owner:** Layer 5 §6.0 — Layer 0 assigns the proposal content to Layer 5, and only an acceptance bullet in Layer 5 acknowledges it.
- **Defect:** for a `require_confirmation` channel, an implementer of Layer 5 has no contract for the proposal it must hand to Layer 0 each cycle: no type, no rule for the `subject` and `proposed_facets` projection, no definition of which inputs make up `proposal_fingerprint`, and no rule for how a Layer-0 approval re-enters Layer-5 admission and with which `ApplyStepSource.kind`. Layer 0 and the Layer-6 occurrence depend on these fields.
- **Proposed direction:** add a short Layer-5 §6.0 subsection defining the recovery-confirmation proposal hand-off and approved-dispatch path that Layer 0 §7.4.1 cites.
- **Confidence:** medium
- **Verification:** pending

### F-X3-03 — `ResponseRequestDeclaration.expires_at` is mandatory, but Layer 5's consent and feedback requests have no expiry instant

- **Category / severity:** O / P3
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:2060` — "expires_at: EvidenceInstant"; `docs/specs/v3/layer0_runtime_spec.md:2077-2079` — "An owner declares each request when it becomes actionable and withdraws it when it closes; only a currently declared, unexpired request accepts a response."; `docs/specs/v3/layer5_action_reactions_spec.md:2611-2612` — "with actions `grant` and `decline` and admitted actors `{"resident"}`, expiring when the request closes."; `docs/specs/v3/layer5_action_reactions_spec.md:2631-2633` — "with actions `done`, `dismiss` and `not_useful`, admitted actors `{"resident"}`, open for as long as the activation lasts and withdrawn at its `closed` phase; there is no separate feedback window."
- **Owner:** Layer 0 §5.1.3 — its declaration type admits no request without a fixed deadline, while two of its three Initial-V3 owners declare open-ended requests.
- **Defect:** the `layer5.household_consent` and `layer5.advisory_feedback` owners must fill a non-optional `expires_at` instant for a request whose end is only its withdrawal; neither layer says which instant to use, and any finite value would make the ingress reject a still-open request as expired.
- **Proposed direction:** make `expires_at` optional (`None` = until withdrawn) in Layer 0 §5.1.3, or have Layer 5 state the value it declares.
- **Confidence:** medium
- **Verification:** pending
