## Findings

### F-X7-01 — The "automatic authorization requires an enabled user-visible binding" check is placed at publication staging, where no binding can be enabled

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer5_action_reactions_spec.md:734-736` — "An automatically authorized resumable Reaction requires an enabled, user-visible binding for this cause; publication staging rejects a missing binding."; `docs/specs/v3/layer5_action_reactions_spec.md:5113-5117` — "Staging a resumable descriptor without `active_channel_unmanaged_after_restart` in its closed applicability map, or authorizing it automatically without an exact enabled user-visible availability binding per resumable channel, fails."; `docs/specs/v3/layer5_action_reactions_spec.md:1364-1366` — "the availability publication bindings Layer 5 declares for it and Layer 6 composes into its generation (Layer 3 §6.3.1; disabled, since the Reaction is not `automatic`)"; `docs/specs/v3/layer5_action_reactions_spec.md:1779-1782` — "An availability binding (Layer 3 §6.3.1) is enabled exactly while its Reaction's mode is `automatic`. After an authority transition that enters or leaves `automatic` commits, Layer 5 hands Layer 6 one typed `BindingEnablementChange` (Layer 6 §9.2) ... the transition never waits for it."; `docs/specs/v3/layer6_notification_spec.md:535-537` — "It rejects ... an automatically authorized resumable Reaction without an enabled user-visible binding for `active_channel_unmanaged_after_restart` (Layer 5 §3.2)."; `docs/specs/v3/layer6_notification_spec.md:520-522` — "A change whose `authority_transition_id` is already applied, or that names a Reaction of another generation, is ignored."
- **Owner:** Layer 5, which states the requirement and owns the authority transition where it can actually be checked; Layer 6 §9.2 restates it as a staging check.
- **Defect:** Every new configuration generation starts `notification_only` and its bindings are composed disabled; `automatic` is reached only through a later authority transition, which is not a staging and which Layer 6 learns of only asynchronously after commit, applying it without any rejection. So the Layer-6 staging rejection never sees an "automatically authorized" Reaction, and a resumable Reaction whose binding is declared `user_visible=False` can be promoted to `automatic`, while Layer 5 §8 requires that authorization to fail.
- **Proposed direction:** Make the user-visible-binding precondition a check of the Layer-5 promotion command (and keep Layer-6 staging to existence/visibility, not enablement).
- **Confidence:** medium
- **Verification:** pending

### F-X7-02 — U4 says `HouseholdConsentAuthority` references are HA user ids; Layer 5 and Layer 6 §5.2 make them `ha_person_id`s

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer6_notification_spec.md:643` — "**U4** — every `HouseholdConsentAuthority` reference is an HA user id (Layer 5 §7.1.1)."; `docs/specs/v3/layer5_action_reactions_spec.md:3964-3965` — "each reference is the `ha_person_id` of a Layer-2 `Person` (Layer 2 §2.8) whose `household_role` is `resident` and whose stored `ha_user_id` is set"; `docs/specs/v3/layer6_notification_spec.md:185-186` — "`consent_authorities` is derived, never configured: the recipients whose `ha_person_id` is in the current `HouseholdConsentAuthority` (Layer 5 §7.1.1)."
- **Owner:** Layer 6 §13, whose U4 summary predates the CA4-118 Person model.
- **Defect:** Read as stated, U4 makes the authority a set of HA user ids, which cannot be matched against recipients' `ha_person_id` as §5.2 does; the owner (Layer 5 §7.1.1) stores Person ids and reaches the HA user through the Person.
- **Proposed direction:** Restate U4 as "every reference is the `ha_person_id` of a resident Person with a stored `ha_user_id`".
- **Confidence:** high
- **Verification:** pending

### F-X7-03 — Layer 6 acceptance tests an action notice of an `environment.*` Reaction, which Layer 5 forbids

- **Category / severity:** C / P3
- **Locations:** `docs/specs/v3/layer6_notification_spec.md:685-687` — "An availability episode, an unconfirmed follow-up and an action notice of a weather-protection Reaction are delivered as `safety` during quiet hours, while the same kinds for an `environment.*` Reaction are held"; `docs/specs/v3/layer5_action_reactions_spec.md:2517-2518` — "In Initial V3 only `safety.weather_protection` declares it; every other descriptor declares `False`."
- **Owner:** Layer 6 §14, whose criterion must be constructible from Layer-5 occurrences.
- **Defect:** No Initial-V3 `environment.*` descriptor has `resident_action_notice=True`, so no `ReactionActionNoticeOccurrence` for an `environment.*` Reaction can exist; the "held" half of the criterion cannot be exercised for the action-notice kind.
- **Proposed direction:** Limit the held case to availability and follow-up (or state it as a unit test of the §6.1 table, not of Layer-5 occurrences).
- **Confidence:** high
- **Verification:** pending

## Observations

- `automation_scope_id` is described by both sides as "the configured Reaction" (Layer 5:2909, Layer 6:495),
  but neither defines its value or its relation to `reaction_id`/generation; Layer 6:521 ignores a
  `BindingEnablementChange` "that names a Reaction of another generation", although the change carries no
  generation id, and Layer 6:345 says the availability input "carries no `reaction_id`".
- Delivered pre-restart advisories keep feedback buttons whose ingress request no longer exists
  (Layer 5:2498-2500 retires only undelivered records); consent has an explicit reissue for this case,
  advisories do not.
- Layer 6 §4.3 maps occurrence fields to scalar `context` entries; Layer 5 defines flattening for follow-up
  facets but not for `ReactionActionNoticeOccurrence.channels` (a tuple of records).
