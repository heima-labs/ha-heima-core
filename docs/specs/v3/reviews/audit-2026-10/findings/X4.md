## Findings

### F-X4-01 — Layer 1 limits the registry-id-suffixed evidence shape to room occupancy; Layer 2 also uses it at casa and for presence, with an HA person id suffix

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer1_substrate_spec.md:249-252` — "A source-level observation may include a stable Heima registry id as its final namespace segment when several observations of the same semantic kind must coexist at one `Location`; Layer 2 reserves this shape for room-occupancy evidence as `occupancy.evidence.<kind>.<sensor_id>`. That suffix identifies the configured logical reading"; `docs/specs/v3/layer2_registries_spec.md:628-630` — "**Casa occupancy evidence follows the same boundary.** … produces `occupancy.evidence.<kind>.<sensor_id>` at `Location(scope="casa")`"; `docs/specs/v3/layer2_registries_spec.md:388` — "`occupancy.evidence.person.<ha_person_id>` at casa reads the HA person's state"; `docs/specs/v3/layer2_registries_spec.md:395` — "one Sensor `presence.evidence.person.<ha_person_id>` at casa"; `docs/specs/v3/layer2_registries_spec.md:355` — "ha_person_id: str # HA person storage id; stable; never the entity_id"
- **Owner:** Layer 1 — it restates which Layer-2 facts use the suffixed shape; Layer 2 owns the namespaces.
- **Defect:** Layer 1 says the suffixed shape is reserved for room-occupancy evidence, suffixed by `sensor_id`. Layer 2 also uses it for casa occupancy evidence and for a second namespace, `presence.evidence.person.<id>`. In the person-derived facts the suffix is the HA person storage id, not a `sensor_id`.
- **Proposed direction:** Layer 1 should state the shape generically, or list every Layer-2 use with its suffix id.
- **Confidence:** medium
- **Verification:** pending

### F-X4-02 — Layer 1 says unavailability is recorded at once and an all-unavailable fusion is unavailable; Layer 2's `unavailable_grace` keeps the last available output

- **Category / severity:** C / P3
- **Locations:** `docs/specs/v3/layer1_substrate_spec.md:457-459` — "Unavailability has to be a positive signal, recorded at the moment the producer cannot form a usable assertion"; `docs/specs/v3/layer1_substrate_spec.md:585-587` — "if every input to a fusion is itself `available=False` this cycle, the derived `HouseFact` is `available=False` too, and none of these functions is called at all"; `docs/specs/v3/layer2_registries_spec.md:1336-1338` — "unavailable_grace: Window | None = None # None: emit unavailable immediately. Otherwise, retain the last committed available output only for this bounded interval when the candidate becomes unavailable"; `docs/specs/v3/layer2_registries_spec.md:1375-1378` — "start or continue one ephemeral availability-grace record … During this interval the committed output remains the rule's deliberate temporal result; no per-cycle fact write occurs"
- **Owner:** Layer 1 — Layer 2's bounded grace is an explicit, reviewed policy; Layer 1's general statement does not allow for it.
- **Defect:** Take a room-occupancy `FusionRule` with `Stability(unavailable_grace=Window(seconds=30))` whose inputs all become unavailable. For up to 30 s the current derived fact stays the last available output, and no `available=False` fact is written. Layer 1 requires `available=False` both at that moment and in that cycle.
- **Proposed direction:** Layer 1 should state the rule as applying to the fusion's raw candidate, and point to Layer 2 §5.2's bounded grace as the one exception for the committed output.
- **Confidence:** medium
- **Verification:** pending

### F-X4-03 — Layer 1 puts `opening_id` on an Actuator channel; Layer 2 defines it on the Actuator only

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer1_substrate_spec.md:911-913` — "An opening's live state is never a Topology field: it comes from a `Sensor` with `related_opening_id` or an `Actuator` channel with `opening_id` (Layer 2 §3, §6)"; `docs/specs/v3/layer2_registries_spec.md:2067-2072` — "class ActuatorChannel: controlled_channel … channel_kind … observable_state_contract_id … actuation_adapter_id … hold_scope" (no `opening_id`); `docs/specs/v3/layer2_registries_spec.md:2081-2083` — "opening_id: str | None = None # which physical opening this actuator operates, when applicable (a shutter) — a mechanical sub-detail of a room-scoped actuator"
- **Owner:** Layer 1 — it names a Layer-2 field at the wrong level.
- **Defect:** `ActuatorChannel` has no `opening_id`. The opening relation belongs to the whole `Actuator`, so all its channels share one opening and no channel can name its own.
- **Proposed direction:** Layer 1 should say "an `Actuator` with `opening_id` (through its registered channels)".
- **Confidence:** high
- **Verification:** pending

## Observations

- Layer 2 §2.4 requires that the suffix of every `occupancy.evidence.<kind>.<sensor_id>` fact
  equal the Sensor's `sensor_id`. §2.8.1 suffixes the core-generated person evidence with
  `ha_person_id` and never says what that Sensor's `sensor_id` is. The rule can be met only if the
  generated `sensor_id` equals `ha_person_id`, and nothing states this.
- Layer 1 §6 says a zone-dependent fact "carries the resolved execution semantic fingerprint in
  `FactSource.configuration_fingerprint`". Layer 2 §2.5 defines that field as the producer's own
  execution semantic fingerprint. The Zone's fingerprint is therefore presumably folded into the
  producer's fingerprint, but neither layer says so.
