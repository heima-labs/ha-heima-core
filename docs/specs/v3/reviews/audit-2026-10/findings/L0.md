### F-L0-01 — `previous_cycle` snapshot "never seeded from durable history" contradicts clean-restart pre-hydration

- **Category / severity:** C / P1
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:846` — "The snapshot starts empty after every process restart. A newly declared or impacted producer key also has no usable predecessor until one complete evaluation under current execution semantics has sealed it; durable history never seeds this view."; `docs/specs/v3/layer0_runtime_spec.md:946` — "At a later bootstrap, before the first DAG, a matching clean marker lets Persistence pre-hydrate the declared previous-cycle keys from the durable state as of that completed cycle."; `docs/specs/v3/layer0_runtime_spec.md:3501` — "After a simulated clean shutdown/restart, the key is pre-hydrated before the first DAG from the matching committed cycle"
- **Owner:** Layer 0 §4.1 (line 846–848): the approved backlog decision "`FactRef.previous_cycle` snapshot and restart semantics, resolved (2026-09-09)" and Layer 2 §5.8 adopt clean-restart pre-hydration, so the absolute sentence is the stale one.
- **Defect:** after an orderly shutdown with a matching `CleanShutdownMarker`, line 846 requires the first cycle's `previous_cycle` reads to be empty/unusable, while line 946 and the §13 criterion require them to be hydrated from durable state. A first-cycle `FormulaStrategy` self-memory or a Layer-5 transition pair gets a different predecessor depending on which rule is implemented.
- **Proposed direction:** restrict line 846–848 to unclean/mismatched restarts and to newly declared or impacted keys, and cross-reference the clean-marker exception.
- **Confidence:** high
- **Verification:** pending

### F-L0-02 — "Every class creates a hold" contradicts the hold qualification rule

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:1834` — "Only `resident` and `physical` controls can be resident learning evidence (Layer 3); every class creates a hold (§6)."; `docs/specs/v3/layer0_runtime_spec.md:3517` — "Every class creates a hold with `origin=\"manual\"` and that `manual_actor`."; `docs/specs/v3/layer0_runtime_spec.md:2328` — "A divergence qualifies only when the channel/facet is registered and currently observable; its current admitted Reaction target was physically confirmed during the present uninterrupted runtime observation epoch; the current valid observation differs under the versioned core matcher"; `docs/specs/v3/layer0_runtime_spec.md:3232` — "Given a confirmed standalone `admin_command` or `recovery` ApplyStep with no current admitted Reaction target, when a later different valid edge arrives, no Reaction hold opens."
- **Owner:** Layer 0 §5 (line 1834) and §13 (line 3517): §6.2 is the detailed normative rule; the §5/§13 sentences should say that no actor class is exempt from a qualifying divergence, not that every manual control creates a hold.
- **Defect:** a verified manual control by a resident on a channel with no physically confirmed current admitted Reaction target (or one equal to the confirmed target) emits `actuator.manual_control`; line 1834 and the §13 criterion require a hold with `origin="manual"`, while §6.2 and the line-3232 criterion require none. A test written from line 3517 would demand a hold that §6.2 forbids, and that hold would block automatic commands.
- **Proposed direction:** rephrase both sentences as "every class can open a hold when the edge qualifies under §6.2".
- **Confidence:** high
- **Verification:** pending

### F-L0-03 — `system.health` notification event fact has no reserved claim or owner

- **Category / severity:** R / P2
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:2994` — "It hands one occurrence per transition, read-only, to Layer 6 (`system.health`) and to Layer 8's health projection"; `docs/specs/v3/layer0_runtime_spec.md:1345` — "`(notification_kind, operation_id)` is the unique key of the record and also the durable identity of its audit event fact (`fact_type=notification_kind`)"; `docs/specs/v3/layer0_runtime_spec.md:677` — "It likewise reserves `reaction.action_notice` (owner `layer6.reaction_action_notice`), `proposal.review_pending` (owner `layer6.proposal_review`) and `reaction.consent_request` (owner `layer6.consent_request`) as Layer-6 event claims"; `docs/specs/v3/layer6_notification_spec.md:84` — "notification_kind: str                 # equals the event fact_type and the Layer-0 claim"
- **Owner:** Layer 0 §4: it reserves the claim of every other Initial-V3 Layer-6 kind, and Layer 6 defers the claim owner to Layer 0.
- **Defect:** delivering a `system.health` notification requires appending a `system.health` event fact under an exclusive `FactTypeClaim` (§4.5, Layer 6 §4.1), but no `FactTypeClaim(fact_type_pattern="system.health", owner_id=…, emission_kind="event")` is reserved anywhere; the `claim_owner_id` of the Layer-6 descriptor for that kind has no defined value, and staging cannot check the claim.
- **Proposed direction:** add a reserved Layer-6 event claim for `system.health` with its owner id next to the other Layer-6 claims in §4.
- **Confidence:** high
- **Verification:** pending

### F-L0-04 — Layer 0 is said to read nothing above it, yet derives `household_role` from the Layer-2 Person registry

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:1087` — "consistent with Layer 0 depending on nothing above it, Persistence never populates that table by reaching upward"; `docs/specs/v3/layer0_runtime_spec.md:1918` — "Layer 0 never reads Layer 2's registry or evaluates the action matcher itself."; `docs/specs/v3/layer0_runtime_spec.md:1842` — "At every authenticated boundary Layer 0 derives `ha_admin` from HA's own permission check and `household_role` from the active Layer-2 `Person` whose stored `ha_user_id` matches the HA user, never from client data."; `docs/specs/v3/layer0_runtime_spec.md:2081` — "derives its `UserActor` (§5: `ha_admin` from HA's permission check, `household_role` from the matching Layer-2 `Person`)"
- **Owner:** Layer 0 §5/§5.1.3: elsewhere Layer 0 receives pushed, resolved inputs instead of reading upward (§4.1 buffer requirements, §4.3 retention floors, §7.4 "receives resolved Actuator policy and fingerprint deltas rather than reading a registry"); the Person lookup has no such pushed contract.
- **Defect:** at the response ingress and the manual-control edge, Layer 0 must map an HA user id to a Layer-2 `Person`'s `household_role`, i.e. read the active Layer-2 Person registry, which lines 1087 and 1918 exclude. The texts do not say what staged `ha_user_id -> household_role` index Layer 2 supplies at generation cutover, so the two rules cannot both hold as written.
- **Proposed direction:** state that Layer 2 pushes a frozen `ha_user_id -> household_role` projection to Layer 0 with each composed generation, as §7.4 does for Actuator policy.
- **Confidence:** medium
- **Verification:** pending

### F-L0-05 — §13 checkpoint criterion says "last-write-wins per entity", while §7.4 merges per facet per channel

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:3494` — "multiple accepted target changes for one entity before the next tick produce one last-write-wins snapshot commit"; `docs/specs/v3/layer0_runtime_spec.md:2626` — "The key is `(actuator_id, controlled_channel)`, not HA `entity_id`."; `docs/specs/v3/layer0_runtime_spec.md:2629` — "For each `ChannelTarget.targeted_facets`, it replaces only that facet's copied value and trusted authority anchor; untouched facets and other channels remain."; `docs/specs/v3/layer0_runtime_spec.md:3299` — "Successive partial targets on one channel replace only addressed facets, including their individual source anchors."
- **Owner:** Layer 0 §13 (line 3493–3496), restating §7.4 imprecisely.
- **Defect:** two partial targets on different facets of one channel, accepted before the same tick, must both survive under §7.4 (and the line-3299 criterion), but a "last-write-wins" snapshot per entity keeps only the second; two channels on one HA entity would also collapse into one key.
- **Proposed direction:** reword the criterion as one merged snapshot per `(actuator_id, controlled_channel)` with per-facet replacement.
- **Confidence:** high
- **Verification:** pending
