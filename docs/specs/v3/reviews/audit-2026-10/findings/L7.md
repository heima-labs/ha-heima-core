## Findings

### F-L7-01 — Calendar input is promised to producers but has no blueprint field and no Layer-0 requirement path

- **Category / severity:** R / P2
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:161` — "the ready calendar timeline snapshot (Layer 0 §3.4.1) when the blueprint declares it;"; `docs/specs/v3/layer7_extensions_spec.md:84-90` — "class ExtensionProducerRole: inputs: tuple[ExtensionInputSlot, ...] claims: tuple[ExtensionClaim, ...] cadence: Window invoke_on_input_change: bool resource_envelope: ResourceEnvelope" (no calendar field; `ExtensionInputSlot` binds only `fact_type`); `docs/specs/v3/layer0_runtime_spec.md:883-884` — "A Layer-5 plan or a core Layer-2 declared-context producer (Layer 2 §2.9) that needs calendar context declares a finite `CalendarViewRequirement` during staging"; `docs/specs/v3/layer0_runtime_spec.md:460` — "Consumers declare their largest upcoming horizon at registration."
- **Owner:** Layer 7 — it promises the input but defines no declaration (entity, horizon) for it; Layer 0 lists the permitted calendar consumers and does not include extensions.
- **Defect:** a blueprint that wants calendar context has no field to declare it, and Layer 0 admits a `CalendarViewRequirement` only from a Layer-5 plan or a Layer-2 declared-context producer, so the entity, horizon, cache prefetch and dependency-index entry for an extension's calendar read are defined nowhere.
- **Proposed direction:** either add a typed calendar requirement to `ExtensionProducerRole` and admit it in Layer 0's calendar-requirement owners, or remove the calendar bullet from §5.
- **Confidence:** high
- **Verification:** pending

### F-L7-02 — Calendar input would expose raw event text that Layer 0 restricts to the Layer-2 classifier

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:161` — "the ready calendar timeline snapshot (Layer 0 §3.4.1) when the blueprint declares it;"; `docs/specs/v3/layer0_runtime_spec.md:889-891` — "The view exposes raw `CalendarWindow` text only to the staged pure Layer-2 `KeywordClassifier`; neither the classifier result nor a policy outcome may persist a calendar summary."; `docs/specs/v3/layer0_runtime_spec.md:401` — "summary: str        # the event's raw text, exactly as HA reports it — unclassified"; `docs/specs/v3/layer7_extensions_spec.md:170` — "No slot may bind `presence@casa`, `household.*`, or any fact about a `Person`, actor, consent or audience"
- **Owner:** Layer 7 — the timeline snapshot it promises consists of `CalendarWindow`s carrying raw `summary`, which Layer 0 does not expose to any consumer but the Layer-2 classifier.
- **Defect:** an extension receiving the ready timeline snapshot reads raw event summaries (for example the "ospiti" event that drives `household.guest_stay`, Layer 2 §2.9), which contradicts Layer 0's text-exposure rule and lets the extension read the source of an excluded `household.*` fact.
- **Proposed direction:** if calendar input is kept (F-L7-01), define it as classified or redacted windows rather than the raw timeline snapshot.
- **Confidence:** medium
- **Verification:** pending

### F-L7-03 — `max_result_age >= cadence + CALIBRATION_WINDOW` does not guarantee that a forced window never expires a healthy fact

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:110-112` — "whose state claim lacks a `max_result_age` or has one shorter than its cadence plus `CALIBRATION_WINDOW` (Layer 3 §5.3.2, so a forced calibration window never expires a healthy fact)"; `docs/specs/v3/layer7_extensions_spec.md:239` — "fixed-delay recurrence after the previous run ends"; `docs/specs/v3/layer7_extensions_spec.md:221-223` — "Results enter staging and are validated at the next `CycleInputBarrier` like any ingress"; `docs/specs/v3/layer3_learning_spec.md:3173-3174` — "During the window no new slow-path run of either class is admitted"; `docs/specs/v3/layer3_learning_spec.md:3178-3179` — "Layer 7 requires `max_result_age >= cadence + CALIBRATION_WINDOW`, so a forced window never expires a healthy extension's fact."
- **Owner:** Layer 7 — it owns the registration bound and the expiry rule; Layer 3 restates the guarantee.
- **Defect:** with cadence 15 min and `max_result_age` 20 min (the minimum accepted), a run ending at t=0 re-arms expiry at about t=20:00; the next run is due at t=15:00, a calibration window opened just before blocks it until about t=20:00, and the result then needs its own run duration plus the next `CycleInputBarrier` (plus any deferral behind a learning slice or the CPU cap), so it arrives after t=20:00 and the healthy fact is written `available=False`. The bound omits run duration, barrier latency and slice deferral.
- **Proposed direction:** state the bound with an explicit margin for run deadline and scheduling delay, or weaken the "never expires" guarantee in both layers.
- **Confidence:** high
- **Verification:** pending

### F-L7-04 — Restart re-arms expiry from the last persisted result, but write-on-change persists only changes

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:292-294` — "Each state claim's expiry job is re-armed from the instant of its last persisted result, as Layer 2 §3.2 checks report age at its first fresh intake: a claim already older than `max_result_age` becomes `available=False` at the first cycle"; `docs/specs/v3/layer0_runtime_spec.md:1016-1017` — "An unchanged fingerprint updates neither history nor queue."; `docs/specs/v3/layer1_substrate_spec.md:446-448` — "For a state fact, `when` is the last accepted state-change instant; it is **not** the last time an identical value was reported"; `docs/specs/v3/layer7_extensions_spec.md:274-277` — "Each instance has a runtime-only state `healthy | backing_off | faulted`."
- **Owner:** Layer 7 — the restart rule relies on a persisted "last result" instant that no layer persists; the only persisted record of a stable state is its last change.
- **Defect:** an extension publishing the same `ext.soil_dryness.index` value every 15 minutes for six hours has its last persisted record six hours old; after a restart that record is older than `max_result_age` (one hour), so the healthy fact is made unavailable at the first cycle even though the last successful run was minutes before shutdown.
- **Proposed direction:** define a persisted last-successful-run instant per state claim (or base restart expiry on the restart instant), and state which record carries it.
- **Confidence:** high
- **Verification:** pending

### F-L7-05 — Input contract gives every bound key a "current committed value", but a slot may bind an event fact

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:69` — "fact_type: str                    # exact core or ext.* fact type; never a pattern"; `docs/specs/v3/layer7_extensions_spec.md:164-165` — "A bound key may be a core fact or another instance's `ext.*` fact; chains of extensions are allowed"; `docs/specs/v3/layer7_extensions_spec.md:158` — "the current committed value of each bound input key, with its `available` flag and provenance;"; `docs/specs/v3/layer7_extensions_spec.md:213-214` — "after a committed change of a bound input, observed through a core-declared committed-state subscription"; `docs/specs/v3/layer0_runtime_spec.md:598-599` — "every emission is durably appended, it has no current-value slot, and it is never read as current state"; `docs/specs/v3/layer0_runtime_spec.md:1692-1693` — "A subscription names one exact state `FactIdentityKey`, never a pattern"; `docs/specs/v3/layer0_runtime_spec.md:1682` — "exact state key; never a pattern, an event type or a scope query"
- **Owner:** Layer 7 — it neither restricts slots to state facts nor defines event-slot semantics, while extensions may themselves declare event claims (§3) that another instance can chain.
- **Defect:** an instance whose slot binds another extension's event claim (or a core event such as `actuator.manual_control`) is promised a current value that Layer 0 says does not exist, and with `invoke_on_input_change` it needs a committed-state subscription that Layer 0 forbids for event types.
- **Proposed direction:** restrict input slots to state facts at registration, or define event-slot input (bounded occurrence history, no change trigger).
- **Confidence:** medium
- **Verification:** pending

### F-L7-06 — Extension analyzer evidence source needs a serving-generation fingerprint that only learners define

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:204-205` — "Its evidence source is `ProposalEvidenceSource(source_kind=\"extension_analyzer\", source_id=instance_id, ...)`, assigned by the runtime (Layer 5 §4.1)"; `docs/specs/v3/layer5_action_reactions_spec.md:1224-1226` — "source_kind: Literal[\"learning_instance\", \"extension_analyzer\"] … serving_generation_fingerprint: str  # that instance's serving generation (Layer 3 §4.1.2)"; `docs/specs/v3/layer3_learning_spec.md:160-163` — "At staging, Layer 3 combines blueprint and instance into one immutable `ResolvedLearningDefinition` … derives separate analysis-definition and serving-generation fingerprints"
- **Owner:** Layer 7 (or Layer 3) — Layer 5 points to Layer 3 §4.1.2 for "that instance's serving generation", but §4.1.2 derives it only for a resolved learning definition, and Layer 7 elides the field with "...".
- **Defect:** for a candidate from an extension analyzer instance, the required `serving_generation_fingerprint` and therefore Layer 5's readiness check (b) ("the recorded `serving_generation_fingerprint` is no longer that instance's active one") have no defined value or change rule (for example, whether a parameter change or a new `implementation_version` changes it).
- **Proposed direction:** define the extension analyzer instance's serving-generation fingerprint and what it covers in Layer 7 §4/§6.
- **Confidence:** medium
- **Verification:** pending

### F-L7-07 — Returned source field: whole-run rejection (§13) is absent from the §8 failure list and differs from Layer 0's sanitize rule

- **Category / severity:** D / P3
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:362-363` — "A returned fact outside the claims, a returned source field, or a value violating its contract rejects the whole run"; `docs/specs/v3/layer7_extensions_spec.md:261-263` — "A run fails on an exception, a missed deadline, a budget rejection, an envelope breach … an event claim emitted more than `max_emissions_per_run` times, or an output that violates its claims or value contracts."; `docs/specs/v3/layer7_extensions_spec.md:188-190` — "Nothing an extension returns sets or changes these fields, and a returned value outside its claims is rejected (Layer 0 §5.1)."; `docs/specs/v3/layer0_runtime_spec.md:1873-1875` — "an untrusted or malformed source is sanitized into a clearly non-authoritative value, never silently trusted. This is what protects against, among other things, a Layer-7 extension returning a source or a fact outside its declaration (Layer 7 §6)."
- **Owner:** Layer 7 — §8 is the normative failure list; §13 adds a failure cause it does not state, and Layer 0 describes the same case as sanitization rather than run failure.
- **Defect:** for a result that carries a source field but otherwise valid claimed facts, §13 discards the whole run (no fact written), §6 only says the fields are not honored, and Layer 0 says the source is sanitized to non-authoritative, which implies the fact is still written.
- **Proposed direction:** add the returned-source case to §8's failure list (or drop it from §13) and align Layer 0 §5.1's wording for extensions.
- **Confidence:** medium
- **Verification:** pending

### F-L7-08 — Layer 0 §4.7 enumerations omit extension consumer references and extension code upgrades that Layer 7 relies on

- **Category / severity:** O / P3
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:142-143` — "Its claims enter the dependency index as producer claims and its slot bindings as consumer references (Layer 0 §4.7)."; `docs/specs/v3/layer7_extensions_spec.md:283-285` — "a new `implementation_version` changes the instance fingerprints, and bootstrap classifies dependents as for any code upgrade."; `docs/specs/v3/layer0_runtime_spec.md:1618-1623` — "every consumer reference on the other — Fusion inputs, Layer-3 `FactSlot`/`SampleBinding` sources, Layer-4 input bindings and upstream claims, Layer-5 trigger, guard, envelope-axis, history, calendar and Actuator-channel bindings, every consumer of a derived Topology or Actuator property … and Layer-6 publication keys."; `docs/specs/v3/layer0_runtime_spec.md:1664-1666` — "If a code upgrade (a changed formula, learning type, resolver kind or descriptor version) makes part of the committed composition invalid"
- **Owner:** Layer 0 — its closed lists of consumer references and code-upgrade triggers do not include extension slot bindings, analyzer learner bindings, or a changed extension `implementation_version`.
- **Defect:** removing a `Sensor` bound by an extension input slot, or removing a learner bound by an analyzer, is not a listed consumer reference for impact classification; a changed `implementation_version` is not a listed bootstrap code-upgrade trigger.
- **Proposed direction:** add extension slot bindings, analyzer learner bindings and extension implementation versions to the Layer 0 §4.7 enumerations.
- **Confidence:** medium
- **Verification:** pending

## Observations (no severity)

- §5 excludes `presence@casa` and `household.*` by name, plus "any fact about a `Person`"; Layer 2
  §2.8.1 also produces `presence.household` and the per-person `presence.evidence.person.<id>` and
  `occupancy.evidence.person.<id>` Sensors. Whether registration (§3, "names a person-related fact")
  rejects these exact fact types is not stated; `occupancy@casa`, declared readable, is derived from
  `occupancy.evidence.person.*`.
- §5's person-exclusion rationale cites "people model invariant 8 and visibility matrix", which live
  in `docs/v3_people_model_draft.md` (not an authoritative layer, and not listed in the registry);
  invariant 8 ("Each presence consumer names its fact") does not itself state that an extension is
  not a resident.
- Layer 0 §8 says an extension run "uses the same boundary" as `AtJob`/`CronEntry` callbacks, while
  Layer 7 §7.1 runs it as slow-path `step(WorkSliceBudget)` work; not contradictory, but the two
  descriptions of the execution boundary differ (interface unit X8).
