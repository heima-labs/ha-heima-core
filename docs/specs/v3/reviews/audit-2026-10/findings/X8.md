# X8 — Layer 7 ↔ Layers 0, 2, 3, 5 (interface)

**Coverage.** Read all of `layer7_extensions_spec.md` (§1–§13) and, on the other side, every passage
that mentions Layer 7, extensions or `ext.*`, plus the sections either side cites: Layer 0 §3.1
(`AtJob` basis, deadline construction), §3.4.1 (calendar placement), §4 (emission semantics, claim

(`LearningProposalCandidate`), §6.4; Layer 5 §2, §4 (candidate validation), §4.1
(`ProposalEvidenceSource`, readiness), §4.2 (composed-generation dependency).

Obligations Layer 7 states about the other layers and found honored: `ext.*` reservation and
`owner_id="layer7.extension.<id>"` (Layer 0 §4); runtime-assigned `kind="extension"` and no upgrade to
`sensor`/`recovery` (Layer 0 §5, §5.1, §13); committed-state subscriptions are core-declared and

(Layer 0 §11); producer role as a third Layer-2 producer kind with a previous-cycle edge (Layer 2

the Layer-3 generation with findings and published results only (Layer 3 §4.1.1, §6.1.1); no models
for extensions (Layer 3 §4.6); no action path, closed candidate-kind registry, `extension_analyzer`
source kind (Layer 5 §2, §4, §4.1). Obligations Layers 0, 2, 3 and 5 state about Layer 7 and found

extension registration mechanism" for calendar. Already recorded and not repeated: F-L7-01/02
(calendar input), F-L7-03 (calibration bound), F-L7-04 (restart re-arm), F-L7-05 (event slots),
F-L7-06 (analyzer serving-generation fingerprint), F-L7-07 (returned source: reject vs sanitize),

(`ShadowPreviewBinding` for proposal producers). No action-path or hot-path invariant violation was
found.

## Findings

### F-X8-01 — Layer 0 says Layer-2 registrations contribute only `state` claims, but the Layer-2 extension producer may declare event claims

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:629` — "Layer 2 registrations contribute only `state` claims."; `docs/specs/v3/layer7_extensions_spec.md:141-142` — "the producer role is a third producer kind in the **Layer-2 generation**, beside `Sensor` and `FusionRule`. Its claims enter the dependency index as producer claims"; `docs/specs/v3/layer7_extensions_spec.md:77` — "emission_kind: FactEmissionKind"; `docs/specs/v3/layer7_extensions_spec.md:112-113` — "whose event claim declares one or lacks a positive `max_emissions_per_run`"; `docs/specs/v3/layer2_registries_spec.md:85-86` — "staged as a third producer kind in the Layer-2 generation beside `Sensor` and `FusionRule` (Layer 7 §4): it declares `ext.*` claims"
- **Owner:** Layer 0 — its claim-composition rule predates the extension producer kind; Layer 2 §2.3 itself limits the state-only rule to `Sensor` and `FusionRule`.
- **Defect:** an extension blueprint with an event claim (legal under Layer 7 §3) is staged as a Layer-2 registration; applied literally, Layer 0's composition rule rejects that claim, so either every extension event claim is unadmittable or Layer 0's rule is false.
- **Proposed direction:** restrict the Layer 0 sentence to `Sensor`/`FusionRule` registrations and name extension producer claims (state or event) as Layer-2-generation claims.
- **Confidence:** high
- **Verification:** pending

### F-X8-02 — Extension `configuration_fingerprint` is "of the active generation", while Layer 0 and Layer 2 make it a per-producer execution-semantic fingerprint no layer defines for extensions

- **Category / severity:** D / P2
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:187-188` — "and the `configuration_fingerprint` of the active generation, which covers `implementation_version`"; `docs/specs/v3/layer0_runtime_spec.md:1733-1735` — "configuration_fingerprint: str | None = None  # resolved per-producer execution-semantic fingerprint, assigned only by its active composed generation"; `docs/specs/v3/layer2_registries_spec.md:248-249` — "`FactSource.configuration_fingerprint` carried by a producer is its resolved execution semantic fingerprint, not an installation-wide generation hash"; `docs/specs/v3/layer2_registries_spec.md:252-256` — "A producer is directly impacted when it is added, removed, relocated, or its execution semantic fingerprint differs; this includes a changed Sensor binding/interpretation/… a changed FusionRule inputs/strategy/formula configuration/stability"
- **Owner:** Layer 7 (or Layer 2, which stages the producer kind) — Layer 7 restates the field with a different meaning and neither layer lists the fields of an extension producer's execution-semantic fingerprint.
- **Defect:** read as the generation's fingerprint, every unrelated commit (for example a Room rename) changes every extension fact's `configuration_fingerprint`, which Layer 2 forbids ("changing a display name is not a reason to … force a fact write"); read as a per-producer semantic fingerprint, Layer 0 §4.7's `semantic_only` classification of extension consumers has no defined input (implementation version, parameters by impact class, slot bindings, claim locations).
- **Proposed direction:** state that the extension producer carries its own execution-semantic fingerprint and enumerate what it covers.
- **Confidence:** medium
- **Verification:** pending

### F-X8-03 — Extension history slots declare a read window, but Layer 0 extends durable retention only for registered learners

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:72` — "history: Window | None            # bounded history read; None reads the current value only"; `docs/specs/v3/layer7_extensions_spec.md:159-160` — "for a slot with `history`, the bounded history of that key through the standard Layer-0 query API (Layer 0 §4)"; `docs/specs/v3/layer0_runtime_spec.md:1089-1092` — "whichever subsystem registers a learner **declares** its retention need against Persistence at registration time … A `fact_type`'s target retention window is the larger of the **14-day** system-wide default and every declared requirement"; `docs/specs/v3/layer3_learning_spec.md:2941-2942` — "each positive `training_window` is compiled with its binding lookbacks/target horizons into per-source retention requirements, and those requirements are registered with Layer 0"
- **Owner:** Layer 7 — it promises a bounded history read but, unlike Layer 3, registers no retention requirement; Layer 0's declaration path names only learner registrations.
- **Defect:** a slot with `history` of 30 days on a fact type no learner binds is retained only 14 days, so the promised history is truncated by design and Layer 7 states no behavior for a `"truncated"` or incomplete read (Layer 0 §4.3 requires a complete-window consumer to refuse such a read).
- **Proposed direction:** have extension staging register each history slot's retention requirement with Layer 0 (and admit that declarant in Layer 0 §4.3), and state the run outcome on truncated or incomplete coverage.
- **Confidence:** medium
- **Verification:** pending

### F-X8-04 — "A due extension always fits" is contradicted by a slow-path memory budget smaller than the largest extension envelope

- **Category / severity:** C / P2
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:218-219` — "a memory reservation keeps the largest enabled envelope admissible"; `docs/specs/v3/layer3_learning_spec.md:3146-3147` — "Before admitting learning work, the planner subtracts from `M_slow` the declared envelope of the largest enabled extension, so a due extension always fits."; `docs/specs/v3/layer3_learning_spec.md:3002` — "`M_slow = max(0, M - B - H)`"; `docs/specs/v3/layer3_learning_spec.md:2982-2983` — "A run whose declared envelope or conservative cost forecast does not fit the current plan is `rejected_resource_budget`"; `docs/specs/v3/layer3_learning_spec.md:3010-3011` — "`lower` is zero or one only when its declared envelope fits the protected budget"
- **Owner:** Layer 3 (with Layer 7's restatement) — the reservation only subtracts from learning capacity; nothing ensures `M_slow` is at least the largest extension envelope, and enablement does not check it.
- **Defect:** on a host where `M_slow` is 64 MiB and an enabled extension declares a 128 MiB envelope, the reservation leaves learning at zero but the extension still does not fit, so every run is `rejected_resource_budget`, a failure under Layer 7 §8, and its state facts expire; both layers state that this cannot happen.
- **Proposed direction:** weaken the guarantee to "fits whenever `M_slow` covers the largest enabled envelope" and state the diagnostic otherwise, or check the envelope against the plan when an instance is enabled.
- **Confidence:** medium
- **Verification:** pending

### F-X8-05 — The extension expiry `AtJob` declares no `basis`, which Layer 0 requires of every owner

- **Category / severity:** O / P3
- **Locations:** `docs/specs/v3/layer7_extensions_spec.md:267` — "Each successful run that publishes a state claim re-arms one ordinary Layer-0 `AtJob` for it (Layer 0 §3.1)."; `docs/specs/v3/layer0_runtime_spec.md:145` — "An owner that cannot classify a job's due is invalid at registration."; `docs/specs/v3/layer0_runtime_spec.md:134-136` — "`wall_clock`: the due expresses an instant defined outside the process (… a Layer-2 `last_reported + max_source_age` expiry)"; `docs/specs/v3/layer2_registries_spec.md:772-773` — "A staged binding with this gate arms one ordinary Layer-0 `AtJob` with `basis=\"wall_clock\"`"
- **Owner:** Layer 7 — it is the job owner; Layer 2 states the basis for the analogous report-age job, Layer 7 does not.
- **Defect:** the expiry due is anchored on the run instant in-process but re-armed after restart from a persisted instant (Layer 7 §9), so `elapsed` and `wall_clock` give different expiry instants across a clock correction; Layer 0 makes an unclassified job invalid at registration.
- **Proposed direction:** declare the basis of the extension expiry job in Layer 7 §8.
- **Confidence:** medium
- **Verification:** pending

### F-X8-06 — Layer 0's closed list of `correlation_id` origin points has no extension run

- **Category / severity:** O / P3
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:2107-2111` — "Origin points: - **A per-cycle evaluation**: one `correlation_id` is minted at the start of each engine evaluation cycle and propagated to every `HouseFact` (Layer-2 sensor/fusion output, Layer-4 semantic claim)"; `docs/specs/v3/layer0_runtime_spec.md:2129-2131` — "Production code paths must do two things explicitly, never rely on the default … mint a genuinely new `correlation_id` at each origin point above"; `docs/specs/v3/layer7_extensions_spec.md:186-188` — "The runtime assigns the `FactSource`: `kind=\"extension\"`, `source_id=instance_id`, `source_type=extension_id`, and the `configuration_fingerprint`"; `docs/specs/v3/layer7_extensions_spec.md:221-222` — "Results enter staging and are validated at the next `CycleInputBarrier` like any ingress"
- **Owner:** Layer 0 — it owns the origin list; Layer 7 lists every runtime-assigned `FactSource` field except `correlation_id`.
- **Defect:** an extension fact is produced by an off-cycle run from inputs of earlier cycles but written in a later cycle; whether it takes the run's own id (like a Layer-3 analysis run) or the applying cycle's id is not covered, so the §13 requirement that a chain be "traceable from a resolved state back to the facts that fed it" has no defined rule for extension facts.
- **Proposed direction:** add an extension run as an origin point in Layer 0 §5.2 (or state that it inherits the applying cycle's id) and name `correlation_id` among Layer 7's runtime-assigned fields.
- **Confidence:** medium
- **Verification:** pending

### F-X8-07 — Layer 5's commit-time `evidence_source_unavailable` rule names only learning instances, but Layer 7 requires the same commit for analyzer instances

- **Category / severity:** O / P3
- **Locations:** `docs/specs/v3/layer5_action_reactions_spec.md:1728-1731` — "The commit that removes or invalidates a learning instance, changes its `serving_semantics`, or makes an evidence artifact unavailable likewise records `evidence_source_unavailable` for every pending proposal whose current evidence it affects (§4.1)"; `docs/specs/v3/layer7_extensions_spec.md:205-206` — "removing or invalidating the instance makes its pending proposals not approvable"; `docs/specs/v3/layer7_extensions_spec.md:379-380` — "Removing an instance whose fact feeds a Fusion and whose analyzer has a pending proposal shows both as dependents, makes the Fusion consumer breaking and the proposal not approvable, in one commit."
- **Owner:** Layer 5 — §4.1's readiness condition (a) covers any source instance, but the §4.2 commit obligation that records it is limited to learning instances.
- **Defect:** removing an extension analyzer instance is not a listed trigger for recording `evidence_source_unavailable` in the removing commit, so Layer 7's "in one commit" acceptance has no Layer-5 rule to rely on.
- **Proposed direction:** extend the Layer 5 §4.2 sentence to extension analyzer instances.
- **Confidence:** medium
- **Verification:** pending

### F-X8-08 — Layer 0 delegates breaking-consumer invalidation to Layer 2 §2.5, which defines none, while Layer 7 relies on it for Layer-2 consumers

- **Category / severity:** O / P2
- **Locations:** `docs/specs/v3/layer0_runtime_spec.md:1644-1646` — "One durable atomic transaction writes the manifest, every new layer generation record, the dependent invalidations that each owning layer defines (Layer 2 §2.5, Layer 3 §4.1.2, Layer 4 §8, Layer 5 §4.2)"; `docs/specs/v3/layer2_registries_spec.md:230-231` — "Any failure rejects the whole candidate and leaves the active generation untouched."; `docs/specs/v3/layer7_extensions_spec.md:165-166` — "a removed upstream instance makes its consumers breaking in the impact preview"; `docs/specs/v3/layer7_extensions_spec.md:287` — "On removal or invalidation, existing rules apply: consumers of its `ext.*` facts are breaking"; `docs/specs/v3/layer7_extensions_spec.md:132-134` — "If no registered producer provides that exact key with a compatible value contract, the instance fails validation"
- **Owner:** Layer 2 — it owns the Layer-2 generation in which both the extension producer and its Fusion or extension consumers are staged, and Layer 0 points to §2.5 for their invalidation; §2.5 defines an impact set for semantic changes but no state for a consumer whose binding breaks.
- **Defect:** removing an extension instance whose fact feeds a `FusionRule` (Layer 7 §13), or removing a Sensor bound by an extension input slot, leaves a Layer-2 consumer without a producer; Layer 2 either rejects the whole candidate (§2.5) or commits it with an invalidation that no Layer-2 rule defines, so the confirmed "breaking" commit Layer 7 relies on has no defined outcome for Layer-2 consumers.
- **Proposed direction:** define in Layer 2 §2.5 the invalidated state of a breaking Fusion or extension-producer consumer (as Layer 3 §4.1.2 does for learning definitions), or state that Layer 7 removal is rejected until such consumers are edited.
- **Confidence:** medium
- **Verification:** pending

## Observations (no severity)

- Layer 2 §2.5's mandatory cutover actions ("re-evaluate and force-write each retained impacted
  producer even when its value is unchanged") cannot run for an extension producer in the cutover
  cycle, because extension code never runs in a cycle (Layer 7 §7.1); until its jittered run, the
  fact computed under the old parameters stays current. When this happens is not stated.
- Layer 7 §3 does not require the analyzer's descriptor to list `learner_proposal` in
  `authoring_modes` (Layer 5 §3), nor exclude `reaction.artifact_adoption` as `candidate_kind`,
  whose payload names no descriptor; a contract of either kind would make every candidate fail
  Layer-5 validation.
- Layer 7 §9 says adding an instance is a mutation "with impact preview and confirmation", while
  Layer 0 §4.7 needs no confirmation for an empty impact record, which a pure addition produces.
- Layer 0 §4.8 delivers each subscriber's current value once after the first cycle; for an
  `invoke_on_input_change` instance this delivery arrives before the first health baseline and is
  coalesced only by Layer 7 §7.2's rules, which the text does not connect.
