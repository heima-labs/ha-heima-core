# CA4-18 — specification impact and scenario review

**Status:** specification reviewed on 2026-10-05. This is a design review, not an
implementation or executable fake-clock result. V3 runtime is not implemented.
**Evidence type:** `textual_contract_and_scenario_review`.
**Runtime test:** `not_run_v3_not_implemented`.

## Approved decision and scope

The backlog [CA4-18](../../../v3_backlog.md) records the approved common scheduling
solution: preserve the existing terminal/nonterminal distinction and give each active
step-programmed Reaction one activation-stable replacement slot. The developer rejected
a light-specific late-off exception. This review introduces no new product rule.

**Owner:** Layer 5 `Shared next-step scheduling slot`.
**Dependencies:** Layer 0 §3.1 for `AtJob` replacement/cancellation; Layer 5 future-step
hold release, comfort trajectory and presence simulation for program-specific selection.
**Affected summaries:** architecture overview and recap.
**V2-to-V3 constraint:** one shared action/scheduling mechanism across descriptors and
Actuator kinds; descriptor policy selects the next eligible step.

## Scenario matrix checked against the written contracts

| ID | Scenario | Contract result | Source |
|---|---|---|---|
| S1 | Same snapshot evaluated twice | One pending job with the same activation key; no re-arm | Layer 5 §6.0, §8 |
| S2 | Required input unavailable, then valid again after the old due time | Same activation; cancel action work; fresh selection of at most one still-eligible next job | Layer 5 §6.0, §7.1.2, §7.2.1 |
| S3 | Stale callback races with replacement or a second evaluation | Revision and selected tuple reject the callback; member admission prevents a second command | Layer 0 §3.1; Layer 5 §6.0, §8 |
| S4 | Committed return, valid plan replacement or authority loss | Terminate or replace the affected activation/slot according to the descriptor; no stale dispatch | Layer 5 §6.0, §7.1.2, §7.2.1 |
| S5 | Calendar outage or guard veto | No invented terminal exit; known due hold-release boundary remains evaluable without a command | Layer 5 §6.0, §7.1.2, §7.2.1 |
| S6 | A resident changes a light while presence simulation is active | Channel hold is governed by the shared hold contract; the next qualifying step can release it without bypassing admission | Layer 5 §6.0, §7.2.1 |
| S7 | A resident changes an HVAC setpoint during comfort trajectory | The same slot and hold release mechanics apply; the descriptor selects a supported future knot | Layer 5 §6.0, §7.1.2 |
| S8 | Heima restarts before a step | No old activation/job is restored; fresh current policy can select one valid next job | Layer 5 §3.2, §7.1.2, §7.2.1 |

**Review result:** the common slot, both Initial-V3 descriptor acceptances, hold release,
Layer 0 cancellation, overview and recap describe compatible responsibilities for these
scenarios. No new contradiction was established in this bounded review. The scenario
statements are written acceptance criteria; no executable fake-clock suite was run.

**Remaining assurance boundary:** this review does not prove every CA4 item or every
possible interleaving. During V3 implementation, execute the fake-clock cases specified
in Layer 5 §7.1.2, §7.2.1 and §8 and record actual test results separately.
