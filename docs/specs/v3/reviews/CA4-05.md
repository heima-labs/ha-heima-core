# CA4-05 — state change, source age and observation gaps

**Status:** specification reviewed (2026-10-07).
**Evidence type:** `textual_contract_and_scenario_review`.
**Runtime test:** `not_run_v3_not_implemented`.

## Approved direction and exact gap

The developer chose to keep `HouseFact.when` as the state-transition instant,
append state facts only on a changed `FactChangeFingerprint`, and represent
observation interruptions separately. Identical reads do not create fact rows
or per-cycle durable confirmation rows. Historical calculations use transition
history plus the existing typed observation/retention coverage. A source whose
failure cannot be detected is not claimed to have been physically reconfirmed.

Layer 1 §4.1 currently says `now - fact.when` alone decides freshness; this
ages a continuously observed stable state from its last change. Layer 3 §4.2
reads the latest *available* state, which can skip a newer unavailable
transition. Layer 2 §3.2 uses HA `last_updated` for a declared source-age gate,
although unchanged HA reports update `last_reported`, not `last_updated`.

## Existing constructs and owners

Layer 0 §4.0/§4.2 owns write-on-change state reconstruction; §4.3/§4.4 already
separate retention from process and required-stream observation gaps. Layer 1
§4.1 owns the meaning of `when` and availability. Layer 2 §3.2 owns optional
`max_source_age` and source normalization. Layer 3 §4.2 owns historical
feature/outcome resolution. Layer 2's valid `available=False` transitions and
Layer 0's `ObservationCoverage` are reused; there is no extra fact kind or
per-reading durable row. Overview, recap, acceptance and registry follow.

V2-to-V3 constraints: one universal HouseFact, no device-specific history
pipeline, bounded declared reads, no invented observations across downtime,
and no unnecessary disk writes on the action path.

## Counterexamples to resolve

| Case | Required result |
|---|---|
| Temperature remains 21 °C through many valid HA reports | One state transition remains; its old `when` alone cannot make a historical state sample stale. |
| A report-driven source stops reporting past staged `max_source_age` | The next evaluation emits unavailable, and historical observation coverage marks the known expiry boundary; an earlier value cannot fill the gap. |
| No unrelated HA event occurs at the report-age deadline | One shared-scheduler `AtJob` checks the registered source just after expiry; a newer report replaces that due and creates no duplicate fact. |
| A change-only source has no declared report-age gate | Its current HA state remains valid until HA reports unavailable or another declared validity rule fails; silence alone cannot prove a physical failure. |
| HA becomes unreadable or Heima restarts | Existing process gap remains incomplete; a returned state begins a new epoch without backfilling missed observations. |
| Source becomes unavailable and later recovers with the same value | The unavailable and available transitions both persist; as-of reads during the unavailable interval cannot skip to the old value. |
| HA reports the same value without changing state or attributes | `last_reported` can satisfy a staged report-age gate; `last_updated` cannot be treated as a report timestamp. |
| Solar geometry source updates without a change to the relevant attribute | Its 30-minute report-age gate follows HA reporting, while geometry remains the value in the frozen snapshot. |

Home Assistant documents the three timestamp meanings in its
[state object documentation](https://www.home-assistant.io/docs/configuration/state_object)
and [last_reported developer note](https://developers.home-assistant.io/blog/2024/03/20/state_reported_timestamp/).

The owner/dependency/acceptance and orientation passages were checked against
the scenarios above. `python3 scripts/check_v3_specs.py` validates the
contract map and references; `git diff --check` checks patch hygiene. These
are specification checks, not executable V3 behavior tests.
