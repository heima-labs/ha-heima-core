# CA4-43 — comfort mode selection impact analysis

**Status:** specification reviewed on 2026-10-05.
**Evidence type:** `textual_contract_and_scenario_review`.
**Runtime test:** `not_run_v3_not_implemented`.

## Current gap

One `HvacTrajectoryBinding` may bind heating and cooling to one channel or
different channels. `ConditioningScope` names only the temperature fact; the
guard profile stores distinct bounds and targets but declares no current
mode selector. Layer 3 has `observed_hvac_mode` as an evidence input, but
Layer 5 has no staged current-cycle `FactRef` for that mode. Its prose says
“in heating season” and “in cooling season” without defining the state that
chooses a season. Selecting the first binding or both would create arbitrary
behavior and possibly a same-channel ownership collision.

## Decision and scenarios

The developer chose an explicit desired mode. The immutable prerequisite
stages either one fixed admin mode or one typed current fact at the conditioned
scope. Layer 3's distinct `(scope, mode)` candidates remain distinct
Reactions; exactly the matching one can be eligible in a cycle. Equipment
observation is a physical compatibility check, not the source that decides
whether to heat or cool.

| ID | Scenario | Required result |
|---|---|---|
| S1 | Shared channel, desired heating | Only heating Reaction eligible; one ownership claim at most |
| S2 | Distinct endpoints, desired cooling | Cooling endpoint selected; heating endpoint confirmed inactive |
| S3 | Selected endpoint observed off | May start selected mode after ordinary admission |
| S4 | Opposing mode active | Safety guard blocks command |
| S5 | Desired mode off | No mode Reaction triggered |
| S6 | Desired fact missing, stale or invalid | Both abstain; no arbitrary endpoint ordering |

**Review result:** the desired source, candidate mode, runtime selection and
physical-state admission are separate and deterministic. No V3 runtime test ran.
